# Frontend Unit Test Runner Implementation Plan

**Date:** 2026-09-01
**Supersedes:** nothing
**Superseded by:** nothing

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development to
> implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Put the frontend's pure modules behind `make verify` with a `node --test` suite that is
type-checked and linted like the rest of the tree.

**Architecture:** No test dependency is added — Node 26 runs `.ts` directly under native type
stripping, so `node --test 'src/**/*.test.ts'` is the whole runner. What the ticket actually builds
is the *gate* around it: a second TypeScript project (`web/tsconfig.test.json`) that type-checks
test files without loosening the base config, an eslint parser project so those files are linted
rather than ignored, and `test-web` folded into `make test` so every pull request runs the suite.
The two existing test files are then rewritten into one convention.

**Tech Stack:** Node 26.7.0 (`node:26-alpine`), `node:test` + `node:assert/strict`, TypeScript 5.x,
eslint 9 flat config with typed linting, GNU make over Docker Compose, Forgejo Actions.

**Spec:** Codeberg issue [#51](https://codeberg.org/DionGerrese/ThatApp/issues/51) — its *Approach*
section is the design of record for this ticket, and its four decisions were settled by the owner on
2026-08-26. Two further criteria were added as a comment on 2026-09-01 (see *Global Constraints*).
Background on why the frontend has no runner: `docs/superpowers/plans/handoff.md`.

## Global Constraints

- **Everything runs in Docker. There is no Go, Node or npm on the host.** Never run `node`, `npm`,
  `npx` or `tsc` bare. Drive everything through `make`, or through
  `docker compose run --rm --no-deps web <cmd>` for anything without a target.
- **A dependency needs a reason the standard library cannot meet.** This ticket adds exactly one
  package, `@types/node`, and it is types-only: no runtime dependency, no test framework.
- **`tsconfig.json` is not to be weakened.** `strict`, `noUncheckedIndexedAccess`,
  `verbatimModuleSyntax`, `isolatedModules`, `noUnusedLocals`, `noUnusedParameters` and
  `noImplicitOverride` all stay exactly as they are, in both projects. No `any`, no `as any`, no
  non-null assertion (`!`) to get past a type error.
- **Scope is pure modules only.** `format.ts` and `duration.ts` today. No DOM shim (jsdom,
  happy-dom), and no unit tests for `router.ts`, `key-column.ts`, `instance-hue.ts`'s
  `paintInstanceDot`, or the `that-*` components — those reach for `document` and stay with
  Playwright.
- **CI does not use Compose, and nothing enforces that the two agree.** `make verify` drives tools
  through containers; `.forgejo/workflows/verify.yml` invokes the same tools directly. **Every
  change to the `verify` chain in the Makefile must be mirrored into that workflow by hand**, in the
  same commit.
- **Do not run `make fmt`.** It is write-only and rewrites seven already-committed files, because
  prettier is pinned `^3.0.0` and the tree has drifted from its own formatter (intake #74). Format
  only the files this ticket touches, by naming them:
  `docker compose run --rm --no-deps web npx prettier --write src/format.test.ts src/duration.test.ts`
- **Formatting matches `web/.prettierrc.json`:** `printWidth: 100`, double quotes, semicolons.
- **Comments are few and earn their place** — a non-obvious "why", a workaround, a subtle invariant.
  Never narrate what the next line does. Several docblocks in this plan are *deletions*: they state
  things that stop being true the moment this ticket lands.
- **Never merge into `main` locally**, and never open the pull request without pasting a green
  `make verify`.

## The convention, defined once

Every task from 4 onward implements this. It is the issue's "a cases table, then `await t.test()`
per row, mirroring Go's `t.Run`".

**Shape.** A parent `test()` takes `async (t)`, declares a typed `cases` table, and loops it,
`await`ing one `t.test()` per row. Each case becomes a named node in the output, one failing case
does not abort its siblings, and the failing input is in the *name* rather than in an assert
message.

```ts
test("a timer is always HH:MM", async (t) => {
  const cases: [number, string][] = [
    [0, "00:00"],
    [60, "00:01"],
  ];

  for (const [seconds, want] of cases) {
    await t.test(`${seconds} seconds is ${want}`, () => {
      const got = timerFigure(seconds);
      assert.equal(got, want);
    });
  }
});
```

**Names.** Parent test names are sentence-shaped lowercase and are kept verbatim from the files as
they stand — this ticket changes their shape, not their claims.

Case names are **derived from the row** by default, so they cannot drift from the data. Where the
existing assert message carries a real explanation rather than a restatement of the input, the row
gains a **leading name column** instead:

```ts
const cases: [string, string, number][] = [
  ["1h75m is 2h15m", "175", 8100],
];

for (const [name, typed, want] of cases) {
  await t.test(name, () => { /* ... */ });
}
```

**Assertions read got/want**, like the Go suite: bind `const got = fn(input);` then
`assert.equal(got, want);` with no message — the diff and the case name already say everything. A
message is kept only where the assertion is a predicate rather than an equality (`assert.ok`), which
has no useful diff of its own.

**A test with a single case is left as a plain `test()`.** A one-row table is noise. This applies to
exactly one test, `"a clock time reads the zone it runs in, not UTC"`.

### Task 1: Type-check the test files

Test files are invisible to `tsc` today. This gives them their own project and the one dependency
that project needs, and wires it into both gates.

**Files:**
- Create: `web/tsconfig.test.json`
- Modify: `web/package.json`, `web/package-lock.json`
- Modify: `Makefile` (the `tsc` target)
- Modify: `.forgejo/workflows/verify.yml` (the `web` job's `Type-check` step)

**Interfaces:**
- Consumes: nothing.
- Produces: `web/tsconfig.test.json`, referenced by name in Task 3's eslint
  `parserOptions.project` array. `@types/node` on `web/package.json`, which is what makes
  `node:test`, `node:assert/strict` and `process.env` resolve in later tasks.

- [ ] **Step 1: Write the config that should fail**

Create `web/tsconfig.test.json`:

```json
{
  "extends": "./tsconfig.json",
  "compilerOptions": {
    "allowImportingTsExtensions": true,
    "types": ["node"]
  },
  "include": ["src/**/*.test.ts"],
  "exclude": []
}
```

Two lines and no more. `allowImportingTsExtensions` is what lets a test write `./format.ts` — node's
ESM resolver requires that extension, and tsc rejects it without this flag. It is legal here only
because the base project sets `noEmit`. `"types": ["node"]` names node's types for this project;
what actually keeps app code from seeing node's globals is the base project's own `"types": []`,
which this project inherits from and then overrides. `"exclude": []` clears the base project's
exclusion of test files, which is the whole point of this file; `tsconfig.worker.json` beside it
does the same thing for `sw.ts`.

- [ ] **Step 2: Run it to verify it fails**

```bash

```

Expected: FAIL. Four `TS2307` errors — `Cannot find module 'node:test'` and
`Cannot find module 'node:assert/strict'`, once each in `src/format.test.ts` and
`src/duration.test.ts`. **This is the RED for this task, and its output belongs in the task report.**
Nothing else should be reported: if any error other than TS2307 appears, stop and report it — it
means a strictness setting bites the test files, which the ticket's refinement found it does not.

### Task 4: Absorb `format.test.ts` into the convention

**Files:**
- Modify: `web/src/format.test.ts` (whole-file rewrite)
- Test: the file *is* the test. `make test-web` is the verification.

**Interfaces:**
- Consumes: Tasks 1–3 — the file is now type-checked, linted and gated.
- Produces: the worked example of the convention that Task 5 follows. Task 5 defines its own local
  `caseName` helper; nothing is exported between test files.

- [ ] **Step 1: Rewrite the file**

Replace the entire contents of `web/src/format.test.ts` with:

```ts
import { test } from "node:test";
import assert from "node:assert/strict";

import { clockTime, timerFigure, totalFigure } from "./format.ts";

test("a timer is always HH:MM", async (t) => {
  const cases: [number, string][] = [
    [0, "00:00"],
    [59, "00:00"],
    [60, "00:01"],
    [9000, "02:30"],
    [36000, "10:00"],
    [-1, "00:00"],
  ];

  for (const [seconds, want] of cases) {
    await t.test(`${seconds} seconds is ${want}`, () => {
      const got = timerFigure(seconds);
      assert.equal(got, want);
    });
  }
});

test("a total is always Nh Nm", async (t) => {
  const cases: [number, string][] = [
    [0, "0h 00m"],
    [2700, "0h 45m"],
    [3600, "1h 00m"],
    [18900, "5h 15m"],
    [36000, "10h 00m"],
    [-1, "0h 00m"],
  ];

  for (const [seconds, want] of cases) {
    await t.test(`${seconds} seconds is ${want}`, () => {
      const got = totalFigure(seconds);
      assert.equal(got, want);
    });
  }
});

/**
 * The rule that matters: a colon is the mark of something you can start and
 * stop. A total growing one would tell the reader a control exists where none
 * does, which is the failure this whole convention is built to prevent.
 */
test("a total never carries a colon", async (t) => {
  const cases: number[] = [0, 59, 60, 3599, 3600, 18900, 359999];

  for (const seconds of cases) {
    await t.test(`${seconds} seconds`, () => {
      const got = totalFigure(seconds);
      assert.ok(!got.includes(":"), `${got} grew a colon`);
    });
  }
});

test("a clock time is always zero-padded HH:MM", async (t) => {
  const cases: [Date, string][] = [
    [new Date(2026, 0, 1, 14, 32), "14:32"],
    [new Date(2026, 0, 1, 0, 5), "00:05"],
    [new Date(2026, 0, 1, 9, 0), "09:00"],
    [new Date(2026, 0, 1, 23, 59), "23:59"],
    [new Date(2026, 0, 1, 0, 0), "00:00"],
  ];

  for (const [date, want] of cases) {
    await t.test(`${date.getHours()}h${date.getMinutes()} is ${want}`, () => {
      const got = clockTime(date);
      assert.equal(got, want);
    });
  }
});

/**
 * The case above builds and reads its Dates from the same local components,
 * so it cannot tell `getHours`/`getMinutes` apart from `getUTCHours`/
 * `getUTCMinutes` — and the container this runs in (`node:26-alpine`, no
 * `TZ`) is UTC, so the two would also agree there by accident. Pinning a zone
 * with a real, known offset from a fixed UTC instant is what makes "local to
 * the browser" an assertion this test can actually fail on.
 */
test("a clock time reads the zone it runs in, not UTC", () => {
  const originalTz = process.env["TZ"];
  process.env["TZ"] = "Europe/Amsterdam";

  try {
    // 13:32 UTC in January is 14:32 CET (UTC+1, outside any DST window) —
    // getUTCHours() would read back "13:32" here instead.
    assert.equal(clockTime(new Date("2026-01-15T13:32:00Z")), "14:32");
  } finally {
    if (originalTz === undefined) {
      delete process.env["TZ"];
    } else {
      process.env["TZ"] = originalTz;
    }
  }
});
```

Four things to notice about what changed, because a reviewer will check each:

- **The nineteen-line docblock is gone.** Every claim in it — "RUDIMENTARY", "not wired into
  `make verify`", "excluded from tsconfig's `include`", "picking either is #51's call" — stopped
  being true in Tasks 1–3. Nothing replaces it: the file no longer needs to explain itself.
- **The last test keeps its plain `test()`** and its docblock. It has one case, and it is the one
  thing here that would be *harmed* by a table.
- **The `"a total never carries a colon"` assertion keeps its message.** `assert.ok` on a predicate
  has no got/want diff, so the message is the only thing that would say what went wrong.
- **Case counts are identical.** No case is added, removed or altered; this is a change of shape.

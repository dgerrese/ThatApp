# Plan — the PWA shell (#12)

**Date:** 2026-08-24
**Supersedes:** nothing
**Superseded by:** nothing

> **For agentic workers:** REQUIRED SUB-SKILL: use `superpowers:subagent-driven-development` to
> implement this plan task by task. Steps are checkboxes; a task ends green before the next begins.

**Goal:** make the app installable and keep it useful with no connection — the shell renders offline,
and the Jira lists it last saw render marked stale.

**Architecture:** a classic-script service worker built as a second esbuild entry, holding a
precache list and a build id the build stamps into it. Two caches, both named by that build id, both
dropped on activation of a new one. Four request classes, of which the load-bearing one is the
fourth: nothing under `/api/` is cached except the two read-only Jira lists.

**Tech Stack:** vanilla TypeScript, esbuild, Go stdlib, Playwright.

**Spec:** `docs/superpowers/specs/2026-08-24-pwa-shell-design.md`. The plan argues from it; read both.

## Why this plan carries no test code

The standing decision from #7, recorded in the handoff: plans here are drafted in #44's light format,
not #6's heavy one. #6's review found six defects in plan-supplied test code, every one an assertion
aimed at the wrong observable — plans are drafted, not verified, and unverified test code in a plan
document is a liability the implementer inherits. Each task therefore names the file, the observable,
and the command that proves it, and the implementer writes the assertion against the code in front of
them.

## Global constraints

Copied from `CLAUDE.md` and the spec; every task inherits them.

- **Everything runs in Docker.** The icon rasterisation was a one-off exception the owner granted on
  2026-08-24 and it is already spent — no task below runs a host tool.
- **No JavaScript frameworks.** Vanilla TS. Tailwind v4, CSS-first, tokens in `@theme`.
- **`index.html` stays under 14,336 bytes** — the TCP initial congestion window. Task 1 makes that a
  test rather than a habit.
- **TypeScript is `strict` with `noUncheckedIndexedAccess`.** No `any`, no `as any`, no non-null
  assertion. Do not weaken `tsconfig.json`.
- **Firefox is the primary target, Chromium is covered, WebKit is a non-goal.** Do not add it.
- **No test contacts a real Jira instance.**
- **Go: stdlib first.** Nothing here needs a dependency; `image/png` is in the standard library.

## The cost this plan runs under

There is no frontend unit-test runner (#51 is open, `status:needs-refinement`). `web/src/format.test.ts`
runs ad hoc under `node --test`, but `make verify` does not run it. So every TypeScript behaviour
below is proven in Playwright, which is slower and coarser than it should be. That is a known cost,
not an oversight; do not invent a runner inside this ticket.

### Task 2 — the worker is built, registered, and activates

**Create** `web/src/sw.ts` — for now only the two constants and empty `install`/`activate` listeners.
It must compile under `strict`; the worker's globals are not the DOM's.

**Create** `web/tsconfig.worker.json` extending `tsconfig.json` with `"lib": ["ES2022", "WebWorker"]`
and `"include": ["src/sw.ts"]`, and **exclude** `src/sw.ts` from the base config. This is why:
`ServiceWorkerGlobalScope` is not in the DOM lib, and the alternative is casting `self`, which is the
kind of cast `CLAUDE.md` tells you the type error is right about. **Modify** the `tsc` target in
`Makefile` to check both configs.

**Modify** `web/build.mjs` — a second `esbuild.build` for `src/sw.ts` with `format: "iife"`,
`bundle: true`, `splitting: false`, `outfile: "dist/sw.js"`. Turn on `metafile: true` for the app
build, and from its outputs compute two values stamped into the worker through esbuild `define`:
`__WD_PRECACHE__`, the list of emitted asset paths, and `__WD_BUILD_ID__`, a hash over their
contents. The list is generated because chunk names carry content hashes and a hand-written one rots
the first time a view is added.

**Modify** `web/src/main.ts` — register `/sw.js` after load, guarded by
`"serviceWorker" in navigator` so a Firefox private window does not throw.

**Test** in `internal/server/server_test.go` — `GET /sw.js` answers as JavaScript. The handler falls
back to `index.html` for anything it cannot find, so this asserts the worker is served as itself
rather than as HTML under a `.js` name — the same failure task 3's install check defends against,
caught one layer earlier and without a browser.

**Create** `.claude/e2e/tests/pwa.spec.ts` — the worker reaches `activated`.

**Verify:** `make verify` and `make test-e2e`. `dist/sw.js` contains the hashed chunk filenames and a
build id.

### Task 3 — install precaches, and refuses to cache a lie

**Interfaces consumed:** `__WD_PRECACHE__: string[]`, `__WD_BUILD_ID__: string` from task 2.
**Produces:** caches named `wd-shell-<build id>` and `wd-data-<build id>`.

**Modify** `web/src/sw.ts` — `install` opens `wd-shell-<build id>`, fetches every entry in
`__WD_PRECACHE__`, and **verifies each response's `Content-Type` against its extension** before
putting it in: `.js` must answer as JavaScript, `.css` as CSS. A mismatch **rejects the install**.
Then `skipWaiting()`. `activate` deletes every cache whose name does not carry the current build id —
shell and data alike — then `clients.claim()`.

The verification is not defensive padding. `handleAsset` falls back to `index.html` for any path it
cannot find, so a missing chunk answers 200 with HTML; caching that poisons the cache with HTML under
a `.js` name, and it surfaces later as a syntax error in a view that used to work. A failed install
leaves the previous worker serving, which is the right outcome.

**Test** in `.claude/e2e/tests/pwa.spec.ts`:

- After activation, `caches.keys()` holds exactly the two current-build caches, and the shell cache
  holds `index.html`, `app.css`, `app.js` and every hashed chunk.
- With a route stubbed to answer HTML for a `.js` precache entry, the worker does not activate and no
  shell cache is left behind. This is the assertion that would fail if someone deletes the
  content-type check as redundant.

**Verify:** `make verify` and `make test-e2e`.

### Task 4 — the shell survives offline

**Modify** `web/src/sw.ts` — a `fetch` listener implementing the first two request classes: hashed
chunks, fonts and icons cache-first; `index.html`, `app.css`, `app.js` and navigations network-first
with a cache fallback. Navigations that miss fall back to the cached `index.html`, which is what makes
`/today` survive a reload offline.

Network-first for the three unhashed files is what removes the environment switch: `make up` and
`make test-e2e` both run `go run -tags dev`, reading assets from disk, so a dev rebuild must always
win while the server is up.

**Test** in `.claude/e2e/tests/pwa.spec.ts`:

- Load, `context.setOffline(true)`, reload: the rail and the view container render.
- Navigate between Today and Settings while offline: both render their shell.
- Back online, rebuild-in-place simulated by changing what the server returns for `app.js`: the next
  load takes the new one rather than the cached one.

**Verify:** `make verify` and `make test-e2e`.

### Task 5 — the two Jira reads cache, and say when they are stale

**Produces:** the `X-WD-Cached-At` response header, an ISO-8601 UTC timestamp.

**Modify** `web/src/sw.ts` — the third and fourth request classes. `GET /api/issues` and
`GET /api/pins` are network-first into `wd-data-<build id>`; when the network attempt fails, the
cached body is returned **with `X-WD-Cached-At` added**, carrying the time the entry was stored.
Everything else under `/api/` is fetched and never cached, on any method.

The fourth class is the rule the design hangs on. `/api/entries` and #9's push are computed from
SQLite on this machine; a cached copy would be a lie about the owner's own work.

**Test** in `.claude/e2e/tests/pwa.spec.ts`:

- Load with issues stubbed, go offline, reload: `/api/issues` resolves from cache and carries
  `X-WD-Cached-At`.
- Offline, `GET /api/instances` fails rather than resolving from cache, even after a successful
  online load populated nothing for it.
- Offline, a `POST` fails and nothing is queued: back online, no write arrives that the user did not
  make again.

**Verify:** `make verify` and `make test-e2e`.

### Task 6 — `api.ts` carries the freshness through

**Consumes:** `X-WD-Cached-At` from task 5.
**Produces:** `type Cached<T> = { value: T; cachedAt: Date | null }`;
`listIssues(): Promise<Cached<IssuesResponse>>`; `listPins(options?: { refresh?: boolean }): Promise<Cached<Pin[]>>`.

**Modify** `web/src/api.ts` — an internal `requestWithMeta<T>(path, init?): Promise<Cached<T>>` that
reads the header, and `request<T>` delegating to it and returning `.value`. **`request<T>`'s signature
does not change**, so `listInstances`, `createInstance`, `updateInstance`, `deleteInstance`,
`testInstance`, `createPin`, `deletePin` and `searchIssues` are untouched. Only `listIssues` and
`listPins` return the wrapper.

The `AbortError` rethrow and the `network_error` mapping stay exactly as they are. The write path
needs no change at all: `request` already turns a failed fetch into
`ApiError(0, "network_error", "Could not reach the dashboard server.")` and every view renders it.

**Modify** `web/src/views/today.ts` — the call sites, taking `.value`. No rendering change yet; this
task is the plumbing and ends with the app behaving exactly as before.

**Verify:** `make verify` — `tsc` is the real gate here, since a missed call site cannot compile —
and `make test-e2e` green with no spec changed, which is the evidence that nothing moved.

### Task 7 — the view says it is showing something old

**Consumes:** `Cached<T>` and `cachedAt` from task 6.

**Modify** `web/src/views/today.ts` — when `cachedAt` is set, render a `wd-alert` with
`tone="warning"` above the affected list, reading *Showing what was here at HH:MM — no connection to
the server.* Format the time through `web/src/format.ts` if it already has the shape; otherwise add
it there, where it is unit-testable under `node --test`, rather than inline in the view.

Amber is correct here: the owner widened it on 2026-08-24 from "not yet sent" to *warning*, of which
"not yet sent" is one instance. Task 8 widens the document to match.

Register an `online` listener that re-runs the refresh the view already has; a successful fetch drops
the header, and the alert clears itself. Remove the listener when the view is torn down — the router
swaps views in place and a leaked listener would refresh a view that is gone.

**Test** in `.claude/e2e/tests/pwa.spec.ts`: offline reload shows the warning with a time; back
online, it disappears without a manual reload.

**Verify:** `make verify` and `make test-e2e`.

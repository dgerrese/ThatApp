**What was clean, and was checked:** no credential was ever committed — `.env` and `*.db` were never

**GitHub's `refs/pull/*` is why the repo could not simply be made public.** Those 39 refs are

## The migration completed, and what it cost

All 80 issue numbers were recreated on Codeberg and verified against the export: zero state, label
or title mismatches across the 78 unaffected slots, and the 26 open issues match the 26 that were
open on GitHub, by number. Both CI jobs passed on Codeberg's hosted runners, so `runs-on:
codeberg-medium` is grantable and the Docker-free workflows work on real infrastructure rather than
only in local simulation. Scoped-label exclusivity was tested rather than assumed: adding
`status/blocked` to an issue holding `status/todo` dropped the latter automatically.

**Three operational limits, all found the hard way.**

Codeberg **rate limits issue creation** far harder than its error message implies — it says 17 per
5 minutes, but one every 20 seconds still tripped it repeatedly. Bulk creation needs roughly one
every 32 seconds. Ordinary single-ticket work never notices.

**Repository create and delete need the `write:user` scope.** This project's token deliberately does
not carry it: the ticket workflow never needs it, and a standing credential able to delete
repositories is a poor trade for saving a manual step. Do those two things in the web interface.

**Actions must be enabled as a repository unit**, and enabling it does not retroactively run
anything — push events that happened while it was off are simply lost. The first run needs a fresh
push or pull request.

**The numbering incident, and the rule it produced.** A pull request was opened while the issue
migration was still running. Forgejo shares one index between issues and pull requests, so the PR
consumed number 49 and the issue meant for 49 landed at 50. A guard comparing each created issue's
number against its planned number caught it and stopped rather than shifting the remaining 117 doc
references by one. The repair was cheap only by luck: 49 and 50 were both pull-request placeholders
with no references pointing at them, so 49 became the real pull request and 50 was retitled. **Never
create an issue or pull request while a numbered migration is running** — and more generally, when a
process depends on a shared counter, nothing else may touch that counter.

A second lesson worth keeping: the first bulk run reported **exit code 0 while having failed**,
because it was piped through `tail` and the pipeline returned `tail`'s status. Do not read an exit
code through a pipe. The failure was only caught by reading the log.

## What the mechanical rename quietly broke

Renaming across the historical documents was the right call for names that still exist in the code —
a reader can grep `that-card` and find it. It has one failure mode worth knowing, found while
cleaning up afterwards.

The environment notes carried a workaround from 2026-08-24: push over HTTPS on `gh`'s token when the
SSH agent is dead, written as a literal command naming
`https://github.com/dgerrese/work-dashboard.git`. The rename rewrote that URL to the Codeberg one.
The sentence then read as current, correct-looking advice — and was nonsense, because `gh`'s token
carries no authority on Codeberg. A stale command that names a dead host announces itself; a stale
command silently retargeted at a live host does not.

**The rule this produces: a mechanical rename is safe for identifiers and unsafe for literal
commands and URLs.** Identifiers are what the code calls things now. A recorded command is a fact
about what was run then, and rewriting it manufactures a claim nobody made. The URL is restored, the
entry says why, and the Codeberg equivalent (`tea login add --git-credentials`) is named as untried.

Worth re-reading the other day logs with this in mind before trusting any command they contain.

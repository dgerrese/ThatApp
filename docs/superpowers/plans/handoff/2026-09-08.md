- **Into v1 against a v2 recommendation:** #39 (extract shared view helpers), #83 (sort the issue

- **Out to v2 against a v1 recommendation:** #43 (`-race` on the Go suite), #101 (the PWA spec's

Read that as: refactors and UI decisions on shipped views are v1 work here, and a flaky gate or an
unstrengthened one is not. v2 is now #13, #43, #47, #53, #101, #110, #111 and #123.

## Mechanics

`tea issues edit <n> --milestone v1` sets it; `--milestone ""` clears it. Milestone membership does
not appear in `tea issues list` output unless `milestone` is named in `--fields`, and the same
`--limit` trap applies as everywhere else on this board.

## A priority axis, asked for off the back of #35

`priority/high` and `priority/low`, created through the API with `exclusive: true` so they behave
like `status/*`. Colours are `#e8590c` and `#9aa5b1`, chosen to sit clear of `bug`'s red,
`status/blocked`'s dark red and `status/needs-refinement`'s yellow.

**Normal priority carries no label**, by the owner's design and for the same reason `status/done`
does not exist: record priority only where it differs from the default. The consequences worth
knowing:

- An unlabelled ticket is **normal, not untriaged**. Do not add a `priority/normal`.
- Exclusivity means `--add-labels priority/high` is the whole move from low, but going *back* to
  normal needs an explicit `--remove-labels`, since there is no third label to displace the current
  one. This is the one place the priority scope behaves differently from the status scope, where
  every transition has a destination label.
- Priority is the owner's to set. Suggest one; never relabel a ticket's priority unasked.

**Nothing has been labelled yet** — the axis exists and the whole board is uniformly normal. The
labels are documented in `CLAUDE.md` and in the `ticket-workflow` skill, which gained a
*Priority* section beside the type axis.

## The local branch list was cleared out

Eighteen stale local branches went after #120 merged, leaving four: `main`, the current
`handoff-2026-09-08`, `worktrees-without-the-tax` — still pushed with no pull request, still
carrying the one patch `main` does not have — and seven awaiting a force delete.

**Rebase-merge is why `git branch -d` refuses half of them.** The forge rebases on merge, so every
commit on a merged branch has a new SHA on `main` and the old tip is not an ancestor of anything.
Those branches read as unmerged however finished they are. `git cherry codeberg/main <branch>` is the
check that tells the truth: it matches patches rather than SHAs, and reports zero not-upstream for
all seven. Run that before force-deleting anything here, and never take "not an ancestor" as
evidence work would be lost.

## #105 and #117 were refined, and the prototype audit finally ran

**#105 is at `status/todo`.** The read half is a client change — `listEntries` already takes a
`from`/`to` range — but the add half is not: `POST /api/entries` drops a client-supplied `day` on
purpose, and both the design of record and the manual-entry design say so in as many words. The
owner chose to **allow the backdated add**, with `POST` gaining an optional `day` and the server
stamping `started_at` at **local midnight of that day**. The browser still never sends a start time
and Week's day strings come out of the rollup the server sent, so the invariant that a `day` and a
`started_at` cannot contradict each other survives intact. Both specs are corrected as part of the
ticket.

Two things travel with it and are folded in. **The announcement carries a day's entries and Today's
listener paints from whatever it is handed**, so a dialog scoped to Monday must announce without a
payload. And **Week listens for nothing at all** — no `onEntriesChanged` anywhere in `week.ts` — so
a cell's dialog can add, edit or delete and the cell behind it keeps its old figure. Day-scoping is
invisible without that.

**The dialog must say which day it is for, and what that looks like is not drawn**, so #105 runs an
interactive design session before planning. The header omits the day deliberately today, on
reasoning that only held while the subject was always today.

**One claim in #105's original body was already false.** The dialog's heading is not blank when Week
opens it — the summary subtitle is omitted deliberately when the ticket carries none, with the

## #8 was brainstormed, and its design is settled but unwritten

The day ended before the spec was written. **Everything below is approved and is what the spec
should say** — it does not need reopening, only writing up, and then a plan.

**The conflict that started it.** The design of record says every Today row offers "a timer and a
duration field". The September prototype, drawn after it, gives a row a duration control and a pin
and draws no start control at all. It does draw the rail's running-timer line. That is undrawn UI,
so it went to the browser companion — `.superpowers/brainstorm/771769-1788881891/content/`, three
options rendered with the prototype's own row markup and tokens.

**Settled in the browser:**

- **A play button in the row's action column, beside the pin.** 34px icon button, ink-muted at rest,
  a green stop square while running. **Both buttons share the one action column** the table already
  has; no second column.
- **No green wash on a running row.** It was drawn and rejected.
- **The Today cell becomes the timer while that row's timer runs** — the live count in green,
  replacing the day's total. That follows `format.ts`'s existing rule: a colon means something you
  can start and stop, `Nh Nm` means a sum you cannot. `timerFigure` already exists and is used
  nowhere; it was reserved for exactly this.

**Settled in the terminal:**

- **Starting a second timer confirms first.** It is not silent.
- **The rail's timer line is a stop control**, so stopping is reachable from any view.
- **Stopping asks for a comment.**
- **The confirm and the comment are one dialog, not two.** Pressing play on another row raises a
  single dialog naming the ticket being stopped and how long it ran, carrying the comment field for
  the entry about to be filed, and its confirm button starts the new timer.
- **Escape cancels the stop and the timer keeps running.** The dialog is a real gate: nothing moves
  until it is committed. That makes the handover atomic on the server too — `POST /api/timer/start`
  carries the displaced timer's comment and does stop-and-start in one transaction, because a stop
  that succeeds beside a start that fails would leave nothing running at all.
- **A timer left running overnight is asked about, not filed silently.** The rail shows it in the
  pending amber reading as left running, with the capped duration, and pressing it asks whether to
  keep the capped entry or discard it. Nothing blocks the app on boot.
- **Discard needs a fourth endpoint** — `DELETE` on the timer resource, ending it and filing
  nothing. The ticket's acceptance criteria name three and must be updated to four.
- **The timer line stays visible on Week**, which reverses the prototype: its script sets the line's
  visibility per view and Week turns it off. That contradicts the rail being how you stop from
  anywhere, so **the drawing is updated** rather than the decision.

**The rest of the design, as approved:**

- A `timers` table exactly as the design of record draws it, primary key checked to `1` so at most
  one row can exist. Starting replaces the row. Deleting an instance cascades.
- **Three states from one row, none stored:** no timer, running, and left running. The third is
  derived by asking whether the timer's start day resolved against `THAT_TIMEZONE` is still the
  current local day — the same rule push state follows, for the same reason.
- **The day boundary.** A stopped timer files an entry whose `day` is the local day it started on,
  whose `started_at` is the real moment work began, and whose length is capped at local midnight of
  that day. No entry spans two days. Table-driven tests against a container clock in UTC.
- **The browser never subtracts two clocks.** The server sends elapsed seconds as of its own
  response; the browser records a monotonic mark at that instant and ticks from it, and re-reads on
  visibility change. A laptop that slept or a clock that drifted cannot invent time.
- `GET /api/timer` answers an explicit empty state, never a 404.

**#8 and #117 collide** — #117 rewrites the rail and Today's rows including the action column #8 adds
a button to. **The owner chose #117 first.**

## The end-of-day run, and two things it turned up

**`git push codeberg "$snap:refs/eod/..."` is broken under zsh.** `:r` is a zsh parameter modifier,
so the unbraced form loses the `:r` and pushes to `...c6cdefs/eod/...`, which git rejects as a
refspec matching nothing. `"${snap}:refs/..."` is the form that works. The `eod` skill's snippet has
the unbraced version. The snapshot for today is at `refs/eod/2026-09-08/handoff-2026-09-08`.

**A push failed once and an identical retry succeeded**, with "Please make sure you have the correct
access rights and the repository exists" — the transient the skill already warns about, seen again.

**Commit signing failed with `1Password: failed to fill whole buffer`**, which is what the agent says
when it is locked: the socket exists and `ssh-add -l` reports no identities. The owner unlocked it
and the commit signed cleanly. Worth knowing that the error names 1Password rather than saying
"locked", so it reads like a corruption rather than a prompt.

**The uncommitted `CLAUDE.md` and `ticket-workflow` changes went to their own branch**,
`project-design-priority-axis`, on the owner's decision — not onto the handoff branch. The end-of-day
routine authors only the handoff, so the dirty tree stopped the run and the owner resolved it.

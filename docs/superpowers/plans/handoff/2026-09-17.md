## #122 shipped, and the first release is out

**The owner merged #148 and #149.** #122 closed with `status/in-progress` still on it, the seventh
time a merge has left one behind; it was stripped by hand.

**Before the merge**, PR #148's CI was confirmed green at `f02d84b`: the release dry run took 3m30s
against the ten-minute cap. On that evidence two criteria were ticked on #122: the pull-request dry
run, and the image holding only the binary and the CA bundle, which the script checks with
`crane export` on the pushed image.

**Cutting the release took three things nobody had written down.**
- The `RELEASE_TOKEN` secret: a personal token with *package: read and write* only, stored under
  the repository's Actions secrets.
- **Releases were disabled on the repository**, so `/releases/new` returned 404. Packages were
  disabled too. The owner enabled both under the unit settings, then tagged `v2026.38.1` on
  `2a90db9` with *Create tag only*.
- **The tag's run was invisible at first.** `actions/tasks` lists only jobs that have started, so a
  three-minute poll saw nothing. `actions/runs` showed run 108 queued behind the two `main` merge
  runs. It waited from 15:27 to 15:56 and then took 3m18s.

**Verified after the release:** the registry served the index for `2026.38.1` and `latest`
(amd64 + arm64) to an anonymous token. `docker pull` succeeded on this machine, which has no Docker
credentials. The amd64 image then ran under throwaway names: `/` returned 200, health `ok`, the
version line printed, `Config.Env` null, and the database survived a restart. Two more criteria
ticked, with the evidence in a comment on #122.

## The owner now runs the release image, and moved the dev database into it

Starting `codeberg.org/diongerrese/thatapp:latest` gave a fresh, empty database, which is what a new
named volume does — not a defect. Two things had to move into the release, and the second is the one
that would have failed silently:

- **All three database files**, not just `thatapp.db`. The dev database is a bind mount at
  `./data`, where `thatapp.db` was 4kB and `thatapp.db-wal` was 2MB. Copying the `.db` alone would
  have moved almost nothing.
- **The secret key.** The key generated for `thatapp.env` differed from `.env`'s, so every stored
  Jira token would have been undecryptable with no visible failure. Compared as hashes, never
  printed.

The owner confirmed the migration worked. **The release container now holds `127.0.0.1:8080` with
`--restart unless-stopped`**, and `.env` still sets `THAT_PORT=8080`, so `make up` and
`make test-e2e` cannot bind until one of them moves. Setting `THAT_PORT=8081` was offered and not
yet answered; the e2e rig reaches the app over the Docker network, so it does not care which port is
published.

## #42 refined and ready

Picked as the next ticket by the ordering rule: `priority/high` and a `bug`, so ahead of #8, which
is high priority but not a defect.

The defect is real and still present. `renderCurrent` already keeps a `navigationId`, but only
`registerTeardown` reads it; nothing checks it after `await load()`. Reading the three views
settled the scope: **each attaches its container to `root` synchronously, before its first await**,
so everything a stale view does later writes into a detached tree. The import await is the only
window, and the fix is a check after it (and one after `view.render`, for the scroll reset).

**The regression test is the open risk, and it is written into the ticket.** Chunks are
`chunk-[hash].js` and Today and Week may share one, so "hold the older view's import" cannot be done
by filename. The plan finds a deterministic ordering or stops and says so.

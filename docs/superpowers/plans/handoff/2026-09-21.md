## #134 refined: the Chromium crash is a Playwright version bug

The owner chose to leave #66 blocked and start #134. Refinement meant measuring it rather than
describing it, and the measurement settled the ticket.

**Fifty full `make test-e2e` runs on `main` at `b623295`**, each ~70s:

| Playwright | runs | crashes |
|---|---|---|
| 1.62.1 | 20 | 5 (25%) |
| 1.63.0 | 30 | 0 |

The 1.62.1 total includes a ten-run control taken *after* the thirty clean runs, which crashed three
times — so machine drift is excluded and the version is the variable. If the old rate held, thirty
clean runs is a 1-in-5,600 coincidence.

**All five crashes were byte-identical**: `SEGV_MAPERR 0x1b0`, same stack offsets frame for frame,
same registers, dying in the *browser* process inside `browser.newContext`. Only the victim test
differed (three distinct ones). So the intake framing was wrong: this is not a family of flaky
failures, it is one deterministic fault with a random bystander. The body now says so.

Two things ruled out along the way, both worth not re-testing:

- **Shared memory.** `ipc: host` is already set *and* Playwright's own default args carry
  `--disable-dev-shm-usage`. Covered twice.
- **"Never seen in CI" as evidence.** `retries: 1` in CI means a crashed test is retried and passes,
  so the run goes green. The CI rate is unknown, not zero.

**Never tested:** whether the local worker count (10, against CI's 4) raises the rate. The version
bump made it moot. It is recorded as the next hypothesis if the bump does not hold, and is named
out of scope on the ticket rather than silently dropped.

One methodological trap, for whoever measures a version next: `npx playwright install` **prunes**
browser builds the current version does not use. Installing 1.63's browsers deleted 1.62.1's from
that container, so reverting with `npm ci` alone produced 524 "executable doesn't exist" failures
that looked like a catastrophic control. Run the control in a fresh container from the image instead.

#134 is refined and at `status/todo`. The fix is a one-line version bump in
`.claude/e2e/package.json` plus its lockfile; the suite passes unchanged on 1.63.0, 513/11/0.

### #139 settled (2026-09-21)

1. **Current week only.** A pinned ticket gets a row in the week containing today and no other; a
   closed week shows what it contained, not what is pinned now. This is the ticket's one special
   case — the row source depends on which week is displayed.
2. **A pin adds its row at once; an unpin leaves it until the view is left.** No new machinery: that
   is already exactly what `addedTickets` (the `Map` in `render()`'s closure) does for search-added
   rows, so the pin control pushes into the same map.
3. **An empty pinned row counts nowhere** — not a day total, not the week total, not the push count.
   Arithmetic, not a choice: no entries means no seconds and no pending entry.

Approach: the server supplies the row (so it survives a reload), the client supplies the immediacy.

### #89 settled (2026-09-21)

**A connection-test verdict is not stored.** In memory for the page's lifetime, no migration, no
column, no cache table. This **overrules** the ticket's own earlier guess that *Not tested* after a
reload "is probably not what is wanted" — a stored verdict is a claim about credentials that can be
revoked elsewhere, so it ages badly. In memory means **the page, not the dialog**: a module-level map
keyed by instance id, so closing and reopening Settings keeps the verdict and only a reload clears
it (decided at refinement, not asked). #89 therefore touches no schema and adds no `THAT_*`.

Raised and deliberately not ticketed: `that-entry-dialog.ts` uses `×` twice, which the language's
icon rule forbids. Named out of scope on #89 and awaiting the owner's word before becoming a ticket.

## #139 shipped as PR #175

Three signed commits on `2399fe8`. Two tasks, each reviewed, plus a whole-branch review — all
APPROVE, no Critical or Important findings.

**The server supplies the row; the client supplies the immediacy.** `handleWeek` reads pins only when
`start == mondayOf(s.now().In(s.cfg.Location))` — deliberately the same expression `weekRangeParam`
uses for its default, so the two cannot disagree about which week is current. `rollUp` seeds an empty
cell block per pinned key it does not already hold; `byDay` never sees it, so no total moves. The
client's pin control calls the existing `onAdd`, which is five lines and **no new state** —
`addedTickets` already had the exact semantics decision 2 asked for.

**The seam was traced from code, not tests**, because that is what a whole-branch review is for: pin
then read, pin then unpin then read, and logging time against a pinned ticket all yield exactly one
row. The rail's push count reads `listEntries()` and shares no code path with `/api/week`.

**The day-boundary test was verified by mutation, twice.** The implementer changed
`mondayOf(s.now().In(s.cfg.Location))` to `mondayOf(s.now())` and watched the test fail; the reviewer
then reproduced that independently rather than accepting the claim. `CLAUDE.md` names the day
boundary one of the two places this system's bugs live — a regression test nobody has seen fail is
not yet evidence of anything.

**A one-off was measured rather than dismissed.** A `table.spec.ts:322` failure appeared once, in a
file this branch never touches. Instead of recording "pre-existing flake", five more full runs were
taken: **one occurrence in 26 runs** of this base, against a twenty-run zero-variance baseline. The
habit that phrase encourages — re-run first, read second — is exactly what let #134 sit unexamined
for seven weeks.

**Known and deliberate, recorded in the PR body:** `weekRangeParam` and `handleWeek` each read
`s.now()` separately. A request crossing local midnight into a new week between the two would show no
pinned rows for that one request, correcting on reload. Fixing it means changing a signature the week
fetch also uses, for a sub-second self-correcting window.

**Two review findings judged and not actioned**, with reasons: the six-Go-test-functions-instead-of-
one-table point does not hold, because `week_test.go` has been one-function-per-scenario since long
before this ticket and matching the surrounding file is its own rule; and comment density matches the
codebase throughout the touched files.

## #39 shipped as PR #177

Three signed commits. `alertFor` had four identical copies and `messageOf` three; both now live in
`web/src/alert.ts`. Verified byte-identical before extraction and diffed against the originals at
review, so it is provably behaviour-neutral apart from one deliberate type change: `alertFor`'s
`tone` narrowed from `string` to the three tones `that-alert` actually accepts, which previously fell
back to `warning` silently.

**`web/tsconfig.json` gained `allowImportingTsExtensions: true`, and that needs to be understood
rather than rediscovered.** `alert.ts` imports `ApiError` as a *value* for `instanceof`, and
`node --test` needs an explicit `.ts` extension to resolve it at runtime; the production config
rejected that with TS5097. It is **not** the weakening `CLAUDE.md` forbids — it permits an import
spelling, touches no strictness setting, and requires `noEmit`/`moduleResolution: bundler`, both
already set. There was no precedent: `fetch-report.ts`'s `"./types.ts"` import compiles only because
it is `import type`, erased under `verbatimModuleSyntax` — the reviewer proved this by checking that
`2399fe8`'s tsconfig lacked the flag while that file already compiled clean.

**A lesson from an intermediate commit:** the implementer first wrote `alert.ts` with a bare
`function` plus a trailing `export { … }`, purely so the brief's grep command would match. Code
contorting to fit a verification command is backwards, and it was reverted — every sibling shared
module uses `export function`. The *criterion* was corrected instead. When a check and the house
style disagree, fix the check.

### What the whole-branch review caught that eight task reviews could not

**The combobox popup drew two hairlines in light and one in dark.** It carried a real border *and*
the new popover shadow's inset ring; in light both resolve to the same colour, in dark the ring is
transparent so it looked correct. A defect in the branch's own new elevation rule, invisible in the
theme the design was authored in. Decision 11 had already answered the same question for dialogs.

Four minor findings came with it, including one worth keeping in mind: **Tailwind v4's `@theme`
extends its defaults rather than replacing them**, so `rounded-2xl` still resolves and a component
could step off the five-step ruler *by name*. The guard was widened rather than closing it by
unsetting the defaults, because unsetting makes an off-scale class an unknown utility that Tailwind
drops silently.

## #99 — the minifier reverses `color-scheme`

Found by opening the app and being asked why nothing looked different. Nothing was stale: the palette
was live in the owner's own browser. But the check turned up a real defect.

```
input:       :root { color-scheme: dark light; }
unminified:  color-scheme: dark light
minified:    color-scheme:light dark
```

`@tailwindcss/cli --minify` reorders it, and the two values are not equivalent. A machine expressing
no colour preference opens the app light where the design says dark.

**The more important half is that the test could not see it.** It asserted against `styles.css` and
passed while the build shipped the reverse. The declaration moved into `index.html`, which the build
copies verbatim; the unit test now reads what ships; and the assertion that would actually have
caught it is in the browser suite, where the minified stylesheet is what executes. Merged as
**PR #100**.

## #95 — begun

Rebased onto #94's merge, planned, and two of six tasks are in.

**One structural question decided the plan's shape and was tested rather than argued.** A custom
element with `display: table-row`, holding `<td>` children inside a `<tbody>`, lays out as a row in
both target browsers with header and body cells sharing their left edges. So `that-ticket-row`
survives as a component instead of being retired into a function returning a `<tr>`, which would have
cost the repo its rule that reusable UI is a `that-*` component.

- **Task 1** — the tooltip and five marks. Two fix rounds, both worth the cost. See below.
- **Task 2** — the table shell. One fix round, on a conflict between the plan and the prototype.

### Three verification failures, all the same shape

Today's recurring lesson, and the reason two fix rounds happened rather than none:

1. **A review finding that measurement contradicted.** The review said `hidePopover()` on a closed
   popover throws, citing the specification, and the fix mirrored an existing guard. Removing the
   guard left every test green. Probing the API directly settled it: **neither `showPopover()` on an
   open popover nor `hidePopover()` on a closed one throws in current Chromium or Firefox.** The
   guards stay as insurance and both comments now say what was measured — including the pre-existing
   one, which had been asserting the same falsehood since the component was written.
2. **A test that proved the wrong thing.** The clipping assertion compared bounding boxes, and box
   geometry is exactly what `overflow: hidden` does not change — it clips paint. So it would have
   passed for a plain positioned div. It now hit-tests what is painted.
3. **A control that passed for the wrong reason.** The fix planted a naive control to prove the
   assertion discriminates, but focusing the trigger scrolled the `overflow: hidden` region to
   `scrollTop: 101`, and the region's `transform` made it the containing block for a `position:
   fixed` descendant — so the control rendered at `y: -55` instead of `46`, off-screen. The hit-test
   found nothing there because the control was not there. **My own prescribed remedy was also wrong**:
   hover scrolls an unreachable target into view too. The real cause was the test's DOM shape, and the
   implementer measured that and corrected me.

### Task 2's conflict, and the ruling

The plan gave `that-table` a `heading` attribute. The prototype puts `.grouph` as a **sibling before**
`.tcard`, never inside it, carrying an instance dot, a name and a right-pinned count and total. The
design document's own rule is that the prototype beats the document, so the plan was wrong. The
attribute was dropped rather than moved, because every value in that header already belongs to the
view and a component taking them would be attribute sprawl.

wrong for finding one closed ticket by key, and widening them changes what the

## A loose end that was not one, and the reading error behind it

`handoff-2026-09-01` was first read as pushed but with no pull request open, and
written up here as work at risk. **That was wrong.** The branch merged as PR #82,
which put remote `main` at `0c1dcfc`, and Codeberg deleted the branch on merge.
Nothing was ever at risk.

The error is worth keeping because it will recur. 1Password was not running, so
`git fetch` could not authenticate — and a failed fetch does not blank the
`codeberg/*` refs, it leaves them frozen at the last successful fetch. Local git
therefore answered confidently and wrongly: a tracking ref for a branch the forge
no longer has, and an ahead-count against a stale `main`. `tea` and the HTTPS API
were working the whole time, because they carry a token rather than the SSH key.
**Checking the forge over the API is what corrected it**, and that is now an
environment note in `handoff.md`.

Second-order lesson: a remote branch that has vanished usually means its pull
request merged. Reading it as a lost push is the pessimistic guess, and it was
the wrong one here.

## #86's CI failed, and #87 fixed it as PR #88

Checking CI on PR #86 turned up a red end-to-end run — the first e2e run this
forge has ever executed, so there was no green baseline to regress from. It
reported 5 failed, 6 flaky, 201 passed, where the same commit is green locally.

The cause was in the run's own first line: `Running 222 tests using 16 workers`.
`codeberg-medium` is 4 CPU / 8G, a figure `.forgejo/workflows/verify.yml`
already records as the reason that workflow is split in two. Playwright had
sized its pool from `os.cpus()`, which inside the runner reports the host's
cores. All five failures and five of the six flakes were Firefox, whose specs
took 25-35s each where the same specs on Chromium took 3-5s. That asymmetry is
what makes this look like an engine bug rather than a starved box, and it is
worth remembering: Firefox is far heavier per instance than Chromium, so it
fails first when a runner is oversubscribed.

The owner approved a ticket on the spot, so #87 was created at
`status/needs-refinement` rather than intake, refined in place, and branched
**from `issue-51-frontend-unit-tests`** at the owner's instruction — that
branch's failing run being the thing under repair.

**A second defect surfaced in the same log.** The trace-upload step ran for the
first time and refused outright: `actions/upload-artifact@v4` aborts on any
non-github.com API. So the run that most needed traces stored none. Swapped for
`forgejo/upload-artifact@v4`, whose tag was confirmed by listing tags on
data.forgejo.org rather than trusted.

**What the reviews were worth.** Both task reviews passed. The whole-branch
review, dispatched with the diagnosis itself put up for challenge rather than
just the edit, upheld the diagnosis on four independent signals and then found
three real text defects: the plan's own Global Constraint told a later session
to declare a blocker if 4 workers was not enough, when the ticket had already
sanctioned lowering it; the config comment's stated reasoning ("half of
`os.cpus()`", "pin to the runner's real size") yields 2, not the 4 the code
picks; and the plan claimed a verification that a green run cannot deliver,
since the upload step is `if: failure()`.

Two rulings went against a reviewer. The whole-branch reviewer's handoff edit
was accepted in substance but moved to this branch, since project-run documents
do not travel in a ticket's pull request. And the re-reviewer's cut of "Two is
the next step down if four still thrashes" was overruled: the plan is
ticket-scoped and gets archived, while the config comment outlives it, so the
fallback belongs in the code.

**The run.** PR #88's own e2e job: `Running 222 tests using 4 workers`, 211
passed, 11 skipped, zero failed, zero flaky, 5m28s inside the 10-minute cap.
The cap made the suite *faster* — 2.0m of test time against 3.3m at sixteen
workers. The upload step resolved its new action and was then skipped, as
predicted, so it remains unfired.

**A base branch chosen wrong, and corrected.** #88 was first opened against
`main`, on the reasoning that a stacked pull request is fragile when the forge
deletes branches after merge. The owner asked whether it should merge into #86
instead, and they were right. Targeting `main` left #86 red with no way to go
green, because its failure is in the rig rather than in anything #51 changed —
so the owner would have been asked to merge a pull request with a failing
check. **A stacked branch merges into the branch it was cut from when that
branch is what it repairs.** #88 was retargeted in place with
`tea api -X PATCH .../pulls/88 -f base=...`; the diff dropped from ten commits
to five and three files.

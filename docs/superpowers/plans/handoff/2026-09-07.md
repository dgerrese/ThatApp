## The machine ran out of inotify instances

`docker compose up` and `make test-e2e` fail on this host, and not because of any code:
`fs.inotify.max_user_instances` is 128, 181 inotify descriptors are open under this user, and the
`web` service's watch step dies with `EMFILE: too many open files`. A bare `docker compose up web`
reproduces it with the branch stashed.

The way around it, used for every browser run in tasks 3 and 4, stays inside Docker and touches no
committed file: `make build-web` (a one-shot build that never enters the failing watch path), then
`docker compose up -d --no-deps app`, then the Playwright profile with `--no-deps` pointed at the
running `app` through its network alias. Raising the limit needs root:

```shell
sudo sysctl -w fs.inotify.max_user_instances=512
echo 'fs.inotify.max_user_instances=512' | sudo tee /etc/sysctl.d/60-inotify.conf
```

## #10 widened, started, and designed

The owner asked for a ticket for fetching worklogs from Jira, then said it belonged inside #10. So
**#113 was created and then closed as `wontfix`, folded rather than declined**, with its open
questions carried into #10's design round rather than dying with it.

That widening changed the ticket's class. #10 alone was bounded: the flows exist, the acceptance
criteria were written, and the Jira client already had update and delete. Adding a fetch gives the
app a direction of data flow it has never had, so the work stepped up to architectural and got a
design document instead of going straight to a plan.

**Four decisions were the owner's and are settled:**

- A 404 on a worklog the app thinks it owns means gone: the delete completes locally, and an update
  creates the worklog afresh and stores the new id.
- #9's lost update closes here rather than in a ticket of its own.
- The fetch finds its issues through a JQL search on worklog author and worklog date, then reads each
  issue's worklogs narrowed by start. The updated-worklogs feed is kept for a future periodic sync,
  which is the shape it actually fits.
- An entry with unpushed local changes is never overwritten by a fetch. Youngest-wins applies only
  where nothing local is at stake, because following the rule literally there would discard an edit
  that was typed and never sent.

**Two facts found by research rather than assumed**, both in the design document: JQL's `worklogDate`
resolves against the Jira server's timezone rather than the user's, so the fetch asks for a day either
side and filters locally on the real start; and where one issue holds more than 100 worklog entries,
JQL's worklog functions only consider the 100 most recent, so such an issue can be missed by the
search. Clockwork's API is real but Pro-only with its own token per instance, and the owner ruled it
not relevant.

The design is `docs/superpowers/specs/2026-09-07-edit-after-push-and-week-fetch-design.md`, committed
as `9209db0` on `issue-10-edit-after-push-and-week-fetch`. #10's body was rewritten to carry both
halves, nine acceptance criteria for corrections and ten for the fetch. **The owner has not reviewed
the design yet** — that gate comes before any plan.

**The blocker clause matters.** The token cannot write worklogs and has never been shown to read them
at the scope the fetch needs. The plan's first task proves both calls against the real instance; if
reads are refused too, #10 stops at `status/blocked` rather than being built against a stub that will
not match production.

## A reported bug that was a stale server, and the trap in it

The owner reported that logging time against Tuesday the 8th put the entry on Thursday the 10th —
today. It was not the code.

`compose.yaml` runs the app as `go run -tags dev ./cmd/server`, which **compiles once when the
container starts**. The source is bind-mounted, so the files change underneath a process that will
never read them again. The web service runs a watcher and rebuilds on every save; the app service
has no equivalent. The owner's container had been up since 19:57 the previous evening.

**The trap is that the stale server was *half*-current.** It answered the new `{ today, entries }`
envelope on reads, because that change was sitting in the working tree the last time the container
started, and the next change — `POST /api/entries` accepting a `day` — was not. Go's `encoding/json`
ignores unknown fields by default, so the browser's `day` was dropped in silence and `started_at`
was stamped from the clock. A half-current server is worse than an obviously old one: the feature
looks present and behaves as though it were broken.

**The discriminator, which cost nothing and wrote nothing:** post an impossible date with an unknown
instance id. Current code validates the day *before* the instance lookup, so it must answer 400;
the stale server answered 404. Before the restart, `instance_not_found`; after it, `day must be a
date of the form YYYY-MM-DD`. That is what turned a suspicion into a fact.

Raised as **#137** at intake: a reloader for the app service, a startup that refuses to serve a tree
it did not compile, or documentation. Only the first removes the trap.

The owner confirmed the feature works after the restart.

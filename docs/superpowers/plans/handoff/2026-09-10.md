## A reported bug that was a stale server, and the trap in it

The owner reported that logging time against Tuesday the 8th put the entry on Thursday the 10th —
today. It was not the code.

`compose.yaml` runs the app as `go run -tags dev ./cmd/server`, which **compiles once when the
container starts**. The source is bind-mounted, so the files change underneath a process that will
never read them again. The web service runs a watcher and rebuilds on every save; the app service
has no equivalent. The owner's container had been up since 19:57 the previous evening.

**The trap is that the stale server was *half*-current.** It answered the new `{ today, entries }`
envelope on reads, because that change was sitting in the working tree the last time the container
started, and the next change — `POST /api/entries` accepting a `day` — was not. Go's `encoding/json`
ignores unknown fields by default, so the browser's `day` was dropped in silence and `started_at`
was stamped from the clock. A half-current server is worse than an obviously old one: the feature
looks present and behaves as though it were broken.

**The discriminator, which cost nothing and wrote nothing:** post an impossible date with an unknown
instance id. Current code validates the day *before* the instance lookup, so it must answer 400;
the stale server answered 404. Before the restart, `instance_not_found`; after it, `day must be a
date of the form YYYY-MM-DD`. That is what turned a suspicion into a fact.

Raised as **#137** at intake: a reloader for the app service, a startup that refuses to serve a tree
it did not compile, or documentation. Only the first removes the trap.

The owner confirmed the feature works after the restart.

### The whole-branch review's findings, which tomorrow starts from

**Critical — the key clause in `SearchText`'s JQL must come out.** `internal/server/issue_search.go`
documents in two places why the exact key lookup goes through `client.Issue` rather than JQL: `key =
"…"` is an *error*, not an empty result, when the project does not exist. So on every instance that
does not hold the key the search 400s and that instance's summary hits are lost with it. A key-shaped
search would report most instances as unsearchable, and the off-list lookup sends exactly that shape
on every cold load. **It buys nothing** — the exact lookup already existed and already satisfied the
criterion.

**This was a plan defect, not an implementer's.** The plan spelled the disjunction out as the JQL to
write, and #84's refinement note "It gains the key" was written without reading the server. The test
that should have caught it cannot: the stub answers any JQL with a hit.

**And the pre-flight conflict scan could not have caught it.** It reasons about files, and this is
two changes colliding inside one request path with no file overlap at all. **That belongs in the
retro** — it is a gap in the scan's own shape rather than a lapse in running it.

### Worth not rediscovering

**Probe git's own signing, not the agent's.** `ssh-keygen -Y sign` against the 1Password socket
succeeded while `git commit -S` still failed, because git signs through `/opt/1Password/op-ssh-sign`
rather than the agent. An empty signed commit, dropped afterwards, is the honest test. A re-sign
attempted on the strength of the wrong probe left a rebase paused mid-way, which looks exactly like a
lost commit and is not — `git rebase --abort` restored both.

**`tea pulls list --state open` and a plain `git fetch` can both answer from stale state.** Two pull
requests showed as absent from the open list while `codeberg/main` still sat at the commit before
them; `git fetch --prune` brought the branch forward and the API confirmed both had merged hours
earlier. Check the API directly before believing either.

**Two spec files still read the real development database** — `pwa.spec.ts` and `settings.spec.ts`
never stub the entries endpoint. A third, `search.spec.ts`, was found and fixed on this branch. That
is evidence for **#35**, not for #84.

### A disagreement the rebase created, raised and not fixed

**The Today sort reads a row's `seconds` attribute, which holds logged seconds only.** A running
row's figure is `seconds + elapsed`, computed at paint time, and the sort observer deliberately
ignores changes inside a cell. So a table sorted by Today does not reorder while a timer runs —
correct, since rows jumping every second would be unreadable — but the visible order can disagree
with the visible figures: a running row reading 3:05 can sit below one reading 3:00.

Neither #8 nor #83 is wrong alone; they were never on one branch until today. It is in #179's body
and is the owner's to make a ticket of.

## #185 raised

The owner then asked for a ticket, and named its shape: **stopping a timer opens a confirm dialog**
with a rounding choice (up or down, 15-minute grid) and an optional description.

Created at `status/needs-refinement`, v1, `enhancement`. Labels and milestone were verified through
the API afterwards, not assumed from the create call. The type is `enhancement` because the ticket
*widens* an agreed contract rather than correcting one — decision 8 of the manual time entry design
put the timer outside the grid deliberately.

Three things the code said that the ticket would otherwise have guessed at:

1. **The description needs no new storage and no Jira work.** `time_entries.comment` has been in
   the schema since the first migration, `store.UpdateEntry` writes it, and the Jira client already
   sends it as an Atlassian Document Format node and omits the field when it is blank.
2. **The 60-second floor is Jira's, not a preference.** `store.MinTimerSeconds` says so in its own
   comment. That turns "what happens to the under-a-minute discard" into a harder question than it
   looked, and it adds a second one: rounding a 7-minute run *down* gives zero, which Jira rejects.
3. **Two paths stop a timer with nobody watching** — `handleStartTimer` stops the running timer to
   start a new one, and `RunningTimer` closes a timer that crossed local midnight as part of
   reading it. Neither can show a dialog.

Those three are the open questions on #185, and all three are the owner's to answer.

### #185 refined the same evening

The owner answered all three open questions in one pass, and the answers collapse into a single
rule rather than three special cases:

> **Up is ceiling to the 15-minute grid. Down is floor to the 15-minute grid. A floor of zero
> discards the entry.**

That is why a 7-minute run rounded down is thrown away, and why "down" doubles as the way to cancel
a mistimed run. The two alternatives put up — clamping at 15 minutes, and hiding "down" below 15
minutes — were both rejected.

On the third question the owner chose to **ask on a timer switch** as well as on a plain stop, on
the grounds that the user is at the screen either way. The midnight close still cannot ask, so that
entry stays honest and `store.MinTimerSeconds` survives for that path alone.

The ticket was rewritten with 15 acceptance criteria and moved to `status/todo`. The body round trip
through the API was verified byte for byte, not assumed. Two things were made explicit in it because
a future reader would otherwise get them wrong: `TestPostEntryAcceptsSecondsThatAreNotAMultipleOf900`
must **not** be tightened, and decisions 3 and 8 of the manual time entry design are **amended by
this ticket** rather than contradicted by it.

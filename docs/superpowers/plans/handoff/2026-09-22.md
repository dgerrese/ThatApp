## How they were captured, and what that cost

A throwaway `.claude/e2e/tests/shots.spec.ts` per branch, stubbing `/api/issues`, `/api/entries`,
`/api/pins` and `/api/week`, run as `--project=firefox` only, writing into `/e2e/test-results/shots`.
Deleted after each capture; nothing was committed to either feature branch.

Three things worth not rediscovering:

- **The e2e container runs as root**, so the PNGs it writes are root-owned and the host cannot delete
  them. Clear them from inside the container — `docker compose --profile e2e run --rm playwright sh
  -c 'rm -rf /e2e/test-results/*'` — not with `rm` on the host.
- **`that-card:first` is the Pinned card**, not an instance card. The first attempt photographed
  "Nothing pinned." three times at 2704 bytes each. Identical file sizes are the tell.
- **A column's first click is not always ascending.** `NATURAL_DIRECTION` in `web/src/table-sort.ts`
  gives Today descending, so one click there sorts most-time-first. Asserting `aria-sort` before each
  shot caught the caption being wrong; the picture alone did not.

The rule's own note about parking the pointer and dropping focus before a shot was followed from the
start and cost nothing. That note earned its place.

### What the demo cost, and the two mistakes in it

**The owner's installed release app runs beside the dev stack, and it holds the default port.** A
second container, `thatapp`, runs `codeberg.org/diongerrese/thatapp:latest` against its own named
volume `thatapp-data`. **Never assume the dev stack's port — read `THAT_PORT` from `.env`, or the
published port from `docker compose ps`.** Ten minutes went into chasing a "stale build" that was
simply the release image, which predates #8 and has no timer at all. The tell was there early:
`curl` returned an `app.js` naming a chunk that did not exist on disk.

**`CLAUDE.md` and the `eod` skill both name a fixed port, and both are wrong on this machine.** That
is where the wrong number came from. Not fixed — it is a project-design change and the owner has not
asked for one.

**Before that was understood, the service worker and caches of the installed app were cleared** —
the owner's own app, not the dev one. It re-registers on the next load and nothing in its
database was touched. Reported to the owner rather than left to be noticed.

**A class toggled on a live timer row is undone within a second.** `paintDuration()` re-runs on every
tick and re-applies `text-running`, so removing the class in the console appears to do nothing. An
injected CSS rule with `!important` holds; a class removal does not.

The demo itself was a running timer on THISHR-9 in the dev app, plus an injected toggle button
flipping the key between the two tones. The timer ran 152 seconds, so stopping it created **entry 62
in the dev database** — unpushed, and left in place pending the owner's word.

## The dev database was emptied of time entries

On the owner's word, all **62** rows of `time_entries` were deleted from `data/thatapp.db`. The
instances (3) and pins (3) were left alone, and `timers` was already empty.

**What that cost, stated because it was stated to the owner before they chose it:** 57 of the 62

**A backup was taken first**, at `data/thatapp.db.backup-20260922T123136`, and it still holds all 62
rows. Restoring is one `cp`. Nothing prunes that file, so it is the owner's to delete when they are
done with it.

Two entries were from today, both `THISHR-9`: the demo timer's 152 s, and a 61 s one this session
did not create.

**Reading the database checkpointed its WAL.** Before the first `sqlite3` call, `data/` held a 4 KB
`thatapp.db` beside a 2.1 MB `-wal`; opening it folded the WAL in and the main file became 57 KB.
That is ordinary SQLite behaviour, not damage, but a session that measures the file size before and
after will see a jump it did not cause.

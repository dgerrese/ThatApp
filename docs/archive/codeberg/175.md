## Body

Closes CB#139.

A pinned ticket now has a row in Week's **current week**, whether or not any time was logged against
it there. The row is an ordinary one — seven em dashes and an em-dash total — indistinguishable from
a row that is there because it was searched for.

#### No design session was needed, and that is worth saying

The row's appearance was settled with the owner on **2026-09-10**. Three shapes were drawn — an
ordinary row, a row whose key carries a pin glyph, and a foot section of empty rows under a thin rule
— and the owner chose the ordinary row. CB#84 then shipped the rendering: `syntheticRow`,
`compareRows` and `mergeRows` already existed, and `week.spec.ts` already asserted the em dashes.

So three of the ticket's five open questions were already answered. Two were settled in conversation
on 2026-09-21, both recorded on the ticket:

1. **Current week only.** A closed week shows what it contained, not what is pinned now — a March
   week carrying five rows of em dashes is noise in a record being reviewed. This is the change's one
   special case and it is deliberate.
2. **A pin adds its row at once; an unpin leaves it until the view is left.**

The third question — whether an empty pinned row counts anywhere — was not a choice. It carries no
entries, so there are nothing to add and no pending entry to count.

#### How it works

**The server supplies the row; the client supplies the immediacy.**

`handleWeek` reads pins only when the requested week is the current one:

```go
if start == mondayOf(s.now().In(s.cfg.Location)) {
    pinned, err = s.db.Pins(r.Context())
    ...
}
```

That is the same expression `weekRangeParam` already uses for its default `start`, deliberately, so
the two can never disagree about which week is current. `rollUp` then seeds an empty cell block for
each pinned key it does not already hold, and everything downstream is untouched — the existing sort
places the row, seven empty cells give zero seconds and a nil push state, and `byDay` never sees it,
so no total moves.

The client's pin control additionally calls the existing `onAdd`, putting the ticket into
`addedTickets` — the `Map` in `render()`'s closure that already gives search-added rows exactly the
semantics decision 2 asks for ("an add lasts until the view is left, full stop"). **No new state, no
pin-change subscription:** five lines in `week.ts`.

#### The seam, traced in review

The two halves can both fire for the same ticket, so the whole-branch review traced it from the code
rather than from tests:

| case | rows | why |
|---|---|---|
| pin, then a read carrying the server's row | **1** | the server's pin loop skips keys already in `byCell`; `mergeRows` filters `addedTickets` against the server's `rows` |
| pin, unpin, then a read | **1** — intended | the server stops sending it, `addedTickets` never deletes, so the row stays until the view is left |
| log time against a pinned ticket | **1**, real figures | same guard server-side; the key is already `known` client-side |

The rail's push count comes from a separate `listEntries()` call with **no shared code path** with
`/api/week`, confirmed by grep.

#### Known and deliberate

`weekRangeParam` and `handleWeek` each read `s.now()` independently rather than sharing one captured
instant. A request that crossed local midnight into a new week between the two would compute its
`start` in the old week and its "current" Monday in the new one, so pinned rows would be absent for
that single request and return on reload. Fixing it means changing the signature of a function the
week fetch also uses, for a sub-second window with a self-correcting symptom. Recorded here rather
than fixed, so the next reader does not re-derive it.

# CB#200: Settings: two saves of the same instance in flight can undo the second

Archived from Codeberg issue [#200](https://codeberg.org/DionGerrese/ThatApp/issues/200), closed. Opened by DionGerrese on 2026-09-23, closed on 2026-09-28.

Labels: `bug`.

Milestone: v1.

**Why it is kept:** Owner decision 2026-09-25 reversing CB#161: Edit is disabled while that instance's save is in flight; why (pre-save values overwrite the first save) and the rejected data-saving marker are not recorded elsewhere.

## Body

Found by the whole-branch review of CB#161 (PR CB#197), 2026-09-23.

#### Problem

Two saves of the same instance in flight at once can undo each other. Save instance A, reopen Edit A, and save again before the first save answers:

- The reopened form was filled from A's pre-save values (the CB#161 test "an Edit form opened on the instance being saved shows the saved values" asserts exactly this while the save is held), so the second save sends those old values in every field the user did not touch. It overwrites the first save on the server.
- When the first save finishes, CB#161's rule rebuilds an enabled Edit A form with the first save's values while the second save is still in flight. The values typed into the pending form vanish from the screen, and a third Save writes the first save's values back.

Both come from one cause: Edit can open on an instance whose save has not answered yet. The reviewer's suggested `data-saving` marker would stop the rebuild but not the overwrite. Saves of **different** instances are not affected: a finishing save only rebuilds a form whose `data-editing-id` matches its own instance, and a create has a new id no form edits.

#### Approach

**Settled by the owner on 2026-09-25, reversing CB#161's decision for this case:** while a save of instance X is in flight, row X's **Edit** button is disabled, and it is re-enabled when that save settles, whether it succeeds or fails.

- A module-level `Set<number>` in `web/src/views/settings.ts` holds the ids with a save in flight. `save()` adds the id before the request and removes it in `finally`.
- The row sets or clears `disabled` on its Edit button from that set. Rows persist across `refresh()` through `patchRow`, which is where the button is updated.
- Test and Remove already disable themselves while they run, so a disabled button is an existing mark; nothing new is drawn.
- With Edit A unreachable while A saves, CB#161's `else if (… data-editing-id="${saved.id}")` rebuild branch in `save()` can never run. Delete it.

#### Acceptance criteria

- [x] While a save of instance A is held open, row A's Edit button is disabled. Rows for other instances stay enabled.
- [x] When that save succeeds, row A's Edit is enabled again, and opening it shows the saved values.
- [x] When that save fails, row A's Edit is enabled again, and the failure reports where CB#161 put it: in the form if it is still shown, otherwise in the page error slot.
- [x] Every CB#161 test in `settings.spec.ts` still passes, except "an Edit form opened on the instance being saved shows the saved values", which is replaced by the criteria above.
- [x] Each criterion has an e2e test in `settings.spec.ts` that holds the PATCH with `holdNextRequest`; the disabled-Edit test fails on main.
- [x] `make verify` and `make test-e2e` are green.

#### Out of scope

- Remove during an in-flight save (`removeInstance()` is unchanged, as in CB#161).
- Disabling any control on other rows.
- Two saves of different instances: traced and not affected.

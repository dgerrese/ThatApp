# CB#307: tab-return.spec's background-tab catch-up test is flaky in Firefox under load

Archived from Codeberg issue [#307](https://codeberg.org/DionGerrese/ThatApp/issues/307), closed. Opened by DionGerrese on 2026-10-09, closed on 2026-10-21.

Labels: `bug`.

Milestone: v1.

**Why it is kept:** Bug investigation with probe evidence (late window focus while hidden consumes the return, 6/6 repro) and the owner's 2026-10-12 decision to fix it in the product, not the test; plan 2026-10-14-focus-while-hidden.md names this issue body as its design of record and does not restate the cause; tab-return.ts states only the rule.

## Body

Found on 2026-10-09 in a full `make test-e2e` run on the CB#301 branch (`349c56e`), which changes only `web/src/settings-dialog.ts`. Seen again on 2026-10-12 on `retro-2026-10-12`, a process-only branch.

#### Problem

`tab-return.spec.ts:238` — "a tab opened in the background catches up when it first becomes visible" — fails now and then in Firefox under the full suite:

```
Locator: locator('#rail-timer')
Expected substring: "WORK-1"
Received string:    "No timer running"
  > 252 |   await expect(railTimer(page)).toContainText("WORK-1");
```

Alone it passes (20 of 20 on 2026-10-09, 10 of 10 on 2026-10-12).

#### Cause

`onTabReturn` (`web/src/tab-return.ts`) counts **any** window `focus` as a return, even while the document is hidden. The test fakes `visibilityState = "hidden"`, but the browser window really has focus. A late real `focus` that lands after the rail's first read and before the outside write uses up the return: `away` goes false, the rail reads nothing new, and the real return (`visibilitychange` to visible) is then ignored.

Reproduced on 2026-10-12 with a probe: the same test with one `window` `focus` dispatched after "No timer running" and before `writeFromOutside` failed 6 of 6, in both browsers, with the exact message above. Not confirmed: that a real `focus` is what arrives in the flaky full runs. The probe shows only that this path gives exactly this failure.

#### Approach — owner's decision, 2026-10-12

Fix it in the product, not only the test. **A `focus` counts as a return only while the document is visible.** A hidden tab is not back, whatever focus it receives. When the guard skips a hidden `focus`, `away` stays true, so the later `visibilitychange` to visible still reads.

The probe becomes a regression test.

#### Acceptance criteria

- [x] In `onTabReturn`, a window `focus` while `document.visibilityState` is `"hidden"` does not run the handler and leaves the tab counted as away.
- [x] A new e2e test in `tab-return.spec.ts`: a tab loaded hidden receives a window `focus`, then an outside write, then becomes visible — the rail shows `WORK-1` and Today's `WORK-2` row reads 1800 seconds. It fails every time with the guard removed (mutation shown in the task report).
- [x] Every existing `tab-return.spec.ts` test still passes, including the window-loses-focus return and "stays visible and focused makes no extra reads".
- [x] The module comment in `tab-return.ts` says that a focus while hidden is not a return.

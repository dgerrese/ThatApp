## Body

Closes CB#39.

`alertFor` had four identical copies and `messageOf` three. Both now live in `web/src/alert.ts` and
every former copy imports them.

#### Nothing to reconcile

The copies were verified identical before any code moved — all four `alertFor` hashing to
`7c8af962cc6af05c2ca1cd21c9485105`, all three `messageOf` to `0e972658ec66eba68e5026afc0fdda4e`. The
whole-branch review then diffed each moved function against its original on `2399fe8` and confirmed
byte equality apart from the `export` keyword and one deliberate type change.

#### One deliberate improvement

`alertFor`'s first parameter was `tone: string`, while `that-alert` accepts exactly three tones and
**silently falls back to `warning`** for anything else. It is now
`tone: "success" | "warning" | "error"`, so a typo is a compile error rather than a quietly
mis-coloured alert. All fourteen call sites already passed literals; none needed editing, and the
review confirmed nothing now falls through to the default that did not before.

#### The one change that needs explaining: `web/tsconfig.json`

`CLAUDE.md` says **"Do not weaken `tsconfig.json`"**, so this is called out rather than buried.

`allowImportingTsExtensions: true` was added to `web/tsconfig.json`. It is needed because `alert.ts`
imports `ApiError` as a **value** — `messageOf` does `error instanceof ApiError` — and `node --test`
requires an explicit `.ts` extension to resolve that at runtime, which the production config
previously rejected with TS5097.

**It does not weaken anything.** The flag permits an import-specifier spelling. It touches no
strictness setting, requires `noEmit` and `moduleResolution: bundler` (both already set), and changes
no other check. `strict` and `noUncheckedIndexedAccess` are untouched.

**Why the main config and not just the test config:** `alert.ts` is production code, type-checked by
`tsconfig.json`, not only by `tsconfig.test.json` — which already carried this flag for test files.

**Why there is no precedent to follow:** `fetch-report.ts` already imports `"./types.ts"` with an
extension, but that is `import type`, erased under `verbatimModuleSyntax`, so it never needs runtime
resolution. The review confirmed this rather than assuming it, by checking that `2399fe8`'s
`tsconfig.json` lacked the flag while that file already existed and compiled clean. `alert.ts` is the
first production module needing a *runtime* cross-module import under `node --test`.

**Rejected alternatives**, both by the implementer and again at review: replacing `instanceof
ApiError` with a structural check (a real behaviour change), and moving `messageOf` into `api.ts`
(contradicts the ticket's explicit "one module exports both"). No Node loader or type-stripping flag
is configured anywhere in the repo that would avoid the extension requirement.

#### The budget is unaffected

`main.ts` imports only `./rail` and `./router`, and `rail.ts` does not reach `push-report.ts`, so
every consumer of `alert.ts` is lazily loaded. Verified from the built `web/dist/app.js`: zero hits
for `"that-alert"` or `"Something went wrong."`.

#### A correction to the ticket's own wording

The first acceptance criterion named the command
`git grep "^function alertFor\|^function messageOf" web/src`, which now returns **zero** hits —
because `alert.ts` uses `export function`, matching every sibling shared module. The code is right
and the command was wrong; the criterion has been corrected on the ticket to
`git grep -nE "^(export )?function (alertFor|messageOf)" -- web/src`, which returns exactly one hit
each.

Worth recording because an intermediate commit on this branch did the opposite — it contorted the
module to a bare `function` plus a trailing `export { … }` so the literal command would match. That
was reverted at review: code should not bend to fit a verification command.

# CB#35: The e2e suite runs against the dev database, not a disposable one

Archived from Codeberg issue [#35](https://codeberg.org/DionGerrese/ThatApp/issues/35), closed. Opened by DionGerrese on 2026-09-01, closed on 2026-09-21.

Labels: `priority/high`.

Milestone: v1.

**Why it is kept:** Owner decision 2026-09-18: dedicated app-e2e service chosen over a separate Compose project or a swapped THAT_DB_PATH, and the per-spec /api/* stubs deliberately stay (they also pin fixtures); the stubs decision is not recorded in .claude/e2e/README.md or elsewhere.

## Body

#### Problem

`make test-e2e` runs the Playwright rig against the Compose `app` service — the same service `make up`
runs. When the dev stack is up, `compose run` reuses that running container, so the suite talks to the
owner's real database (`./data/thatapp.db`, a bind mount since CB#73), under the real
`THAT_SECRET_KEY`, with real Jira instances configured.

Every spec that reaches a view making a Jira call stubs `/api/*` today, so nothing reaches Jira. That
rests on discipline: the next spec that forgets a stub fans out to the owner's real sites, which breaks
`CLAUDE.md`'s "no test ever contacts a real Jira instance". It also makes the suite non-hermetic —
a local run depends on whatever the developer's database holds, so a local failure and a CI failure
need not mean the same thing.

CI is already hermetic: `.forgejo/workflows/e2e.yml` starts the server against a fresh
`$RUNNER_TEMP/e2e.db` with a random key. This is a local-only exposure.

#### Approach

Decided with the owner on 2026-09-18: **a dedicated e2e app service**, not a separate Compose project
and not a swapped `THAT_DB_PATH` on the shared `app`.

- A second service in `docker-compose.yml`, in the `e2e` profile, built from the same `dev` target
  and sharing the Go build caches, so it does not rebuild from cold.
- Its database lives inside the container and is thrown away with it. `make test-e2e` removes the
  service before each run, so every run starts empty.
- A throwaway `THAT_SECRET_KEY`, never the one in `.env`.
- No host port. The rig reaches it over the Compose network under its own alias, which — like
  `that-app` — must not be a gTLD (see `.claude/e2e/README.md` on why `app` was not usable).
- `playwright` depends on it instead of on `app`.

#### Acceptance criteria

- [ ] `make test-e2e` runs the suite against a server whose database is created empty for that run
      and discarded after it. Nothing the suite does can read or write `./data/thatapp.db`.
- [ ] That server runs under a throwaway secret key, not the `THAT_SECRET_KEY` from `.env`.
- [ ] `make test-e2e` works with `make up` running, and leaves the dev stack untouched — its container
      is not restarted and its database is not opened. It also works with nothing running.
- [ ] A spec asserts that the e2e server starts with no instances (an unstubbed `GET /api/instances`
      answers `[]`), so pointing the rig back at a populated database fails locally.
- [ ] The rig's default base URL (`playwright.config.ts`, and the fallbacks in `tooltip.spec.ts` and
      `router.spec.ts`) and the Compose `THAT_BASE_URL` name the new alias, and agree.
- [ ] `.claude/e2e/README.md` describes which server the rig runs against and why.
- [ ] `.forgejo/workflows/e2e.yml`'s `paths:` still names every file the rig depends on. CI's own
      server start is unchanged.
- [ ] `make verify` and `make test-e2e` are green.

#### Out of scope

- **Removing the per-spec `/api/*` stubs that only keep Jira out.** Decided with the owner on
  2026-09-18: they stay. They also pin each spec's fixtures, and removing them is a separate cleanup.
- CI's workflow, which is already hermetic.
- Where the dev database lives.
- Any wording change to `CLAUDE.md` this makes necessary goes in its own project-design pull
  request, not this ticket's.

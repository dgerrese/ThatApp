# CB#217: tooltip.spec.ts's keyboard-focus test uses .focus(), not a real Tab

Archived from Codeberg issue [#217](https://codeberg.org/DionGerrese/ThatApp/issues/217), closed. Opened by DionGerrese on 2026-09-23, closed on 2026-09-28.

Milestone: v1.

**Why it is kept:** Test investigation: a programmatic .focus() with no earlier pointer input matches :focus-visible in both browsers, so such tests do not prove keyboard focus; the reason specs use a real Tab is not recorded in any living doc.

## Body

Found by the CB#107 investigation, 2026-09-23.

#### Problem

`tooltip.spec.ts`'s "focusing the trigger by keyboard shows the tooltip too" focuses with programmatic `.focus()`, not a real Tab. On main the tooltip reveals on any `focus`, so the test is not wrong today, but it does not prove what its name says: a keyboard user's focus. Once CB#107 gates the reveal on `:focus-visible`, the test passes only because a `.focus()` with no earlier pointer input happens to match `:focus-visible` in both browsers (measured).

Three other specs make the same claim through the same accident, against CSS `:focus-visible` rules:

- `pins.spec.ts` (~line 562), the pin control's focus colour — its own comment calls it "a real focus assertion"
- `week.spec.ts` (~line 1401), "a cell takes the hover wash on keyboard focus"
- `search.spec.ts` (~line 674), which hovers before focusing, so hover alone already gives the colour and the focus step proves nothing

**Scope settled by the owner on 2026-09-25: all four, in one pull request.** The same pattern being added on the CB#143 branch is flagged to CB#143's own review, so this ticket does not depend on the order the two merge in.

#### Approach

Reach each target with a real keyboard press.

- **tooltip.spec.ts:** `mountTrigger` appends the trigger at the end of `<body>`, after the whole shell, so insert a plain `<button id="before">` immediately before `#trigger` (with `?.before()`, not a non-null assertion). `.focus()` `#before` — safe, it carries no tooltip and is not what is asserted — then press `Tab`, assert `#trigger` `toBeFocused()` and the tooltip visible; press `Shift+Tab` instead of `.blur()` and assert it hidden.
- **pins, week, search:** focus the element just before the target and press `Tab` (or `Shift+Tab`), asserting `toBeFocused()` before reading the style. In `search.spec.ts`, move the pointer away first, as `pins.spec.ts` already does. If a spec needs several presses, move `smoke.spec.ts`'s `tabUntilFocused` into a shared helper rather than copying it.

#### Acceptance criteria

- [x] The tooltip test reaches `#trigger` with `page.keyboard.press("Tab")`, asserts it is focused, then asserts the tooltip is shown; it leaves with a key press and asserts the tooltip is hidden.
- [x] The pins, week and search tests above reach their target with a real Tab or Shift+Tab, with the pointer moved off the target first.
- [x] No test whose name or comment claims keyboard focus or `:focus-visible` puts focus on its target with `.focus()` — checked with a grep across `.claude/e2e/tests/`.
- [x] Passes in Firefox and Chromium.
- [x] `make verify` and `make test-e2e` are green.

#### Out of scope

- `.focus()` uses that test focus being kept, scrolling or Enter handling, not keyboard reveal (entries, table, timer, the other search sites, and tooltip's hover-then-focus release-order tests).
- Any change to `that-tooltip.ts`; the `:focus-visible` gate is CB#107's.

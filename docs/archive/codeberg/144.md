# CB#144: Today's instance cards leave holes: a short card wraps under a tall one instead of filling the space beside it

Archived from Codeberg issue [#144](https://codeberg.org/DionGerrese/ThatApp/issues/144), closed. Opened by DionGerrese on 2026-09-16, closed on 2026-10-09.

Milestone: v1.

**Why it is kept:** Rejected layouts with reasons (CSS multi-column rebalances under the pointer; grid-lanes flagged off in Firefox/Chromium) are not in the spec or plan, which record only the two-stack outcome.

## Body

#### Problem

Today's instance cards sit in a strict two-column grid (`grid-cols-2` from the content column's
80rem container query, drawn as `.instgrid` in the prototype). A grid row is as tall as its tallest
card, so cards of very different heights leave holes.

Seen with three instances: A holds many tickets, B a few, C none. A and B share the first row; C
wraps to the second row under A — while the space next to A and under B stays empty and is easily
big enough for C.

#### Approach

Settled with the owner in a design session on the local browser companion, 2026-10-09.

**Two stacks, shortest first.** From the 80rem breakpoint, the instance cards go into two column
stacks. Cards are placed in instance position order, and each card goes to the stack that is
shorter at that moment; a tie goes to the left stack.

**Placement is remembered, not recomputed on every redraw.** Today redraws its instance cards on
many events — a pin added or removed, the pins arriving after the issues, the tab regaining focus,
the network returning. None of those may move a card to the other stack. The view keeps each
instance's stack, and computes placement again on two events only:

- **Navigation** — Today is opened.
- **Refresh** — the owner presses the Refresh control.

An instance that appears on a redraw without a remembered stack goes to the shorter stack.

Options rejected in the session:

- **CSS multi-column** (`columns: 2`): no JavaScript, but the browser rebalances the columns when a
  card grows, so a card can change column under the pointer.
- **Native CSS masonry** (`display: grid-lanes`): on by default in Safari only; behind a flag in
  Firefox and Chromium.
- **Manual ordering** of instances is its own ticket, [#28](https://github.com/dgerrese/ThatApp/issues/28). It decides the order cards are placed
  in, not their stack, so it does not reopen these holes.

**Pinned and off-list do not change.** Their grid holds two fixed sections, not a list of cards:
Pinned owns the left half permanently and off-list the right half when it has rows. They stay
locked in place.

#### Acceptance criteria

- [x] At and above the 80rem container breakpoint, instance cards are laid out in two stacks, placed
      in instance position order, each to the shorter stack; a tie goes left.
- [x] The reported case is fixed: with A tall, B short and C empty, C sits under B in the right
      stack, not under A.
- [x] Below the breakpoint, the cards are one column in instance position order (A, B, C).
- [x] Placement is computed when Today is opened and when Refresh is pressed, and on no other
      redraw.
- [x] Adding or removing a pin, the pins arriving after the issues, the tab regaining focus and the
      network returning redraw the cards without moving any card to the other stack.
- [x] An instance with no remembered stack goes to the shorter stack on the redraw it appears in.
- [x] Crossing the 80rem breakpoint while Today is open switches between one column and two stacks
      without a reload.
- [x] Document order follows the stacks, left stack top to bottom then right stack, so tab order,
      row arrow keys and screen reader order match what is on screen.
- [x] Cards in the two stacks still share one key column width (`alignKeyColumn` over the results).
- [x] The Pinned / off-list grid is unchanged.
- [x] The prototype's Today and the visual language describe the two stacks in place of
      `.instgrid`'s grid.
- [x] The placement rule is covered by a table-driven test that a plausible refactor would fail,
      including the tie and the remembered-stack cases.
- [x] An end-to-end test with uneven card heights passes in Firefox and Chromium.
- [x] The pull request attaches light and dark screenshots of Today with uneven cards.

#### Out of scope

- Ordering instances by hand — [#28](https://github.com/dgerrese/ThatApp/issues/28).
- More than two stacks. The design's "never three" stands.

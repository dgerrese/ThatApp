# CB#281: Focus falls to <body> when the entry dialog's busy state disables its save button

Archived from Codeberg issue [#281](https://codeberg.org/DionGerrese/ThatApp/issues/281), closed. Opened by DionGerrese on 2026-10-06, closed on 2026-10-09.

Milestone: v1.

**Why it is kept:** Owner decision to keep the native disabled attribute over aria-disabled (stay close to HTML standards, first rule of ARIA) and accept focus on body while busy; this standing preference is not in living docs (CB#297 repeats it; this one is kept).

## Body

Found on 2026-10-06 by the whole-branch review of CB#208. Approved and refined by the owner on 2026-10-08.

#### Problem

A keyboard user presses Enter on the entry dialog's save button (`Add entry`, or `Save` while an entry is edited). `save()` calls `setBusy(true)`, which sets `disabled` on the button and on the duration field (`that-entry-dialog.ts`). A disabled element cannot hold focus, so the browser moves focus to `<body>` — the HTML standard's focus fixup rule, in Firefox and Chromium alike. `setBusy(false)` re-enables the controls but does not return focus. The keyboard user has lost their place inside an open modal, after a failed save **and** after a successful one.

The stop dialog had the same defect; CB#208 fixed it there by returning focus to the pressed button after a failure (`that-stop-dialog.ts`, `confirm()`).

#### Decisions

- **Keep the native `disabled` attribute.** The owner wants the app as close to the HTML standards as possible. `aria-disabled` would keep focus on the button, but the first rule of ARIA is not to use it where a native attribute does the job, and `disabled` also blocks clicks and Enter without our code. The cost is accepted: while the request runs, focus is on `<body>`, and nothing can be pressed then anyway.
- **Repair focus when the busy state ends**, in the same way as the stop dialog.

#### Approach

- In `save()`, record `document.activeElement` before `setBusy(true)`.
- After `setBusy(false)` — on success and on failure — if focus is no longer inside the dialog and the recorded element is still inside it, focus the recorded element.
- Only restore when focus was lost. Enter in the comment field triggers `save()` too; the comment field is never disabled, so its focus stays and must not be moved.
- The success path re-renders the entry list and resets the foot form, but the save button is the same element (only its `label` changes), so it remains the restore target.

#### Acceptance criteria

- [x] After a **failed** save started from the save button with the keyboard, the save button has focus once the error shows.
- [x] After a **successful** save started from the save button with the keyboard, the save button has focus once the dialog is idle again.
- [x] After a save started with Enter in the comment field, focus stays in the comment field, on success and on failure.
- [x] The save button and the duration field still carry `disabled` while the request runs.
- [x] The stop dialog's behaviour does not change.
- [x] Playwright tests cover the three focus cases above, in Firefox and Chromium, each proven by mutation (remove the restore, see it go red).

#### Out of scope

- Moving any dialog to `aria-disabled`.
- Focus while the request runs.
- The delete path, which already returns focus through `refocusIfLostFromDialog`.

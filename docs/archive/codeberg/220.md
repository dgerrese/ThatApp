# CB#220: CI runs on a self-hosted runner instead of Codeberg's shared pool

Archived from Codeberg issue [#220](https://codeberg.org/DionGerrese/ThatApp/issues/220), declined (`wontfix`). Opened by DionGerrese on 2026-09-23, closed on 2026-11-04.

Labels: `wontfix`.

Milestone: Dev stack and CI.

**Why it is kept:** Declined self-hosted Forgejo runner: decline reason (Codeberg disabled Actions, [CB#284](284.md)), rejected mirroring to another forge, and the fork-PR-on-own-host security concern; handoff.md still calls it the lasting answer, which is stale.

## Body

Asked for by the owner on 2026-09-23, after Codeberg's shared runners stopped taking jobs at about 16:04 and every run sat `waiting` for over an hour.

#### Problem

Every job runs on `codeberg-medium`, Codeberg's shared hosted pool. When that pool is busy or stalled, all CI waits, however small the change. The same pool imposes the ten-minute job cap that forced the e2e split (CB#186) and the two-job verify, and it has no Docker daemon, which is why CI runs the tools natively while `make verify` runs them through Compose — the drift `CLAUDE.md` warns about.

#### Direction, settled with the owner

**A self-hosted Forgejo runner, registered on Codeberg.** The workflows stay in `.forgejo/workflows/` and results still land on Codeberg pull requests; only `runs-on:` changes. **It runs on an always-on host, not the development machine**, which is not on all the time. Mirroring to another forge was considered and rejected: two forges, status sync back to Codeberg, and no gain over a runner of our own.

#### To settle at refinement

- **The host.** Which machine or VPS, and how large. The e2e job runs Playwright with `workers: 4`, sized to `codeberg-medium`'s four vCPUs.
- **Pull requests from forks.** The repository is public. Establish whether Forgejo on Codeberg runs a fork's workflow on a self-hosted runner without approval; if it can, that is arbitrary code on the owner's host, and it needs an answer before registration.
- **Isolation.** The runner's Docker backend, not host execution; what the job containers may reach.
- **Whether CI moves to the `make` targets through Docker**, which removes the CI/Compose drift, or only changes the runner label. The first may also undo the e2e split and the two-job verify, since the cap goes away.
- **The release job**, which pushes to Codeberg's registry with a token: stays on `codeberg-medium`, or moves to the new runner.
- **When the host is down.** Jobs wait for it rather than falling back; whether that is acceptable, and how an outage is noticed.
- **The runner's registration token and how the host is set up** — documented in the repository, reproducible, with no secret committed.

#### Acceptance criteria

To be written at refinement.

# CB#79: A failed Jira call discards Jira's own explanation, so the failure cannot be diagnosed

Archived from Codeberg issue [#79](https://codeberg.org/DionGerrese/ThatApp/issues/79), closed. Opened by DionGerrese on 2026-09-01, closed on 2026-09-21.

Labels: `bug`.

Milestone: v1.

**Why it is kept:** Owner decision: Jira's failure body goes to the server log, not the UI; showing it on screen was declined (new line across Today, Week, push reports). Not recorded in the log-jira-failures plan or specs.

## Body

#### Problem

A push failed against the Ridgeline instance, and the UI said:

> RIDGE-4930 — Jira rejected the email and API token

The credentials were fine: `POST /api/instances/{id}/test` succeeded against the same instance and
returned the right account. Jira's actual response was:

```
POST .../rest/api/3/issue/RIDGE-4930/worklog -> 401
{"code":401,"message":"Unauthorized; scope does not match"}
```

Jira said exactly what was wrong, and the app threw that sentence away.

`statusError` in `internal/jira/client.go` reads up to 2kB of the body into the error it returns, so
the information exists. Every Jira failure then goes through **one function**, `instanceErrorFor` in
`internal/server/instances.go`. It is reached through `writeInstanceError` and `instanceErrorBody`
from push, issues, pins, fetch, search and the instance handlers. That function reduces the error to a
code and a fixed message, and it logs only in its `default` branch. A *classified* failure, such as
this 401, leaves no trace anywhere. Diagnosing it took a temporary `log.Printf` patched into
`statusError` and a rebuild.

#### Decision

Settled with the owner on 2026-09-18: **the server log, not the UI.** Nothing changes in the API
or on screen. What Jira said is recorded where `docker compose logs app` shows it.

#### Acceptance criteria

- [ ] Every error `instanceErrorFor` maps is logged once, classified or not. The line carries the
      method, the request path, the status, and Jira's body as `statusError` captured it.
      Today's unexpected-error line keeps its meaning.
- [ ] No logged line carries the account email or the API token, because neither is part of the
      wrapped error. A test asserts it for a 401.
- [ ] A table-driven test captures the log output for a 401, a 403, a 404, a 5xx and an unmapped
      status. It asserts each line holds the path, the status and the body's text. It runs against
      an `httptest.Server`, never a real Jira.
- [ ] The code and message each response carries are unchanged, so no frontend or API test has to
      move.
- [ ] `make verify` is green.

#### Out of scope

- Showing Jira's message in the UI. It was declined for now, because it would put a new line on
  screen across Today, Week and the push reports.
- Classification: the 401/403 conflation that produced the misleading sentence, and the unmapped 429.
  That is CB#19.

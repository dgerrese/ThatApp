# CB#80: Settings: explain what an API token needs before it can push worklogs

Archived from Codeberg issue [#80](https://codeberg.org/DionGerrese/ThatApp/issues/80), closed. Opened by DionGerrese on 2026-09-01, closed on 2026-09-23.

Labels: `enhancement`.

Milestone: v1.

**Why it is kept:** Design sessions for the info and external marks with rejected alternatives the body says not to relitigate (bare i, 1.7 stroke, opened interior; bare arrow), plus the token-scope table; the visual-language spec keeps only the outcome.

## Body

#### Context

The **Add an instance** form in Settings asks for a name, site URL, account email and API token,
and says nothing about what kind of token will actually work. A token that reads fine can still
fail every write.

That is not hypothetical — it happened on 2026-09-01. Assigned issues listed correctly and the
connection test passed, and the end-of-day push then failed on every entry with:

```
POST .../rest/api/3/issue/RIDGE-4930/worklog -> 401
{"code":401,"message":"Unauthorized; scope does not match"}
```

The token carried read access but not whatever a worklog write needs. Nothing in Settings had
warned that this was a distinction, and nothing in the connection test caught it, because the
test only exercises a read.

An information box on the Settings page, next to the token field, is the ask: what to create,
where, and what it must be able to do.

#### What a token needs

Checked on 2026-09-18 against what the app calls and Atlassian's REST documentation. These are the
classic scopes:

| Scope | What the app does with it |
|---|---|
| `read:jira-user` | `GET /rest/api/3/myself`, the connection test |
| `read:jira-work` | the assigned-issue search, single-issue reads, worklog reads |
| `write:jira-work` | worklog add, update and delete, which is the end-of-day push |

An unscoped ("classic") API token carries all three. A scoped token needs all three selected, and
`write:jira-work` is the one that is easy to miss, because a token without it lists issues and passes
the connection test. The granular equivalent for worklog writes is `write:issue-worklog:jira`.
Tokens are created at `https://id.atlassian.com/manage-profile/security/api-tokens`.

#### Decisions

Settled with the owner on 2026-09-18:

- **Static guidance plus a link, not verification.** The connection test cannot check a write scope
  without writing to a real issue, and Jira has no side-effect-free write to probe with. A write probe
  was declined.
- The copy names the three scopes and links to Atlassian's token page, so if Atlassian renames its
  token types again, the link still leads to the current truth.

**Placement, settled in the design session of 2026-09-18: a note under the four fields, above the
buttons** (option B). It is a hairline box in the edge tone with a muted info mark, neither a card nor
an alert. It reads: "Use an unscoped API token, or a scoped one with `read:jira-user`
`read:jira-work` `write:jira-work`. Without `write:jira-work` your issues still list, but pushes
fail. **Create a token ↗**". The scopes are set in mono, and the link is in the primary colour. The
owner chose it over the token field's own helper line (A), which had no room for the warning, and a
disclosure (C), which hides the guidance from exactly the person who needs it. The prototype gains
the note.

#### The info mark, settled in the design session of 2026-09-21

This ticket was blocked from 2026-09-21 because its note called for "a muted info mark" and **no info
mark existed** — not in `web/src/icons.ts`, not in `web/index.html`, not in the prototype's `p-*`
symbols — while Decision 6 of `2026-09-03-visual-language-design.md` enumerates the set the app needs
without one. Inventing a glyph for the shared set was refused; it was settled with the owner on the
browser companion instead.

**The mark is a circled i, in the set's own vocabulary, rendered at 18px:**

```
<circle cx="12" cy="12" r="8.5"/><path d="M12 8.6h.01M12 11.4v3.6"/>
```

- The **same `circle r="8.5"` at 12,12** that `success` and `failed` already use, so it is visibly a
  member of the family.
- The interior is **`warning`'s dot-and-stem inverted** — dot above, stem below — and the dot uses
  the set's existing convention of a zero-length round-capped stroke (`h.01`).
- **1.9 stroke**, round caps and joins, `currentColor`, on the 24px grid. It needs **no exception**
  to the weight rule.

**It is drawn at 18px, not 16px, and that is the whole point of the session.** At 16px the gap
between dot and stem is 1.87px against a 1.27px stroke — less than two stroke widths — and the two
fuse into one blob. Three candidates were shown at 16px and the owner rejected the legibility of
both circled options. At 18px the gap is 2.1px against a 1.43px stroke and it reads.

18px is not a new size: the visual language already renders marks "at 16px in the rail's nav and 18px
in a row control". The note is neither context, so this ticket records it as the note's size.

**Rejected, with reasons worth not relitigating:**

- **A bare i with no circle.** Quieter, and the hairline box already does the containing — but every
  other mark in the set is enclosed or solid, and this would be the odd one out.
- **The same mark at 1.7 stroke**, following the Settings cog's recorded exception. Thinning the
  stroke does not widen the gap, which is what actually fails, so it did not help. It would also have
  cost the set a second weight exception.
- **Opening the interior** (`r=9`, dot at 7.6, a longer stem). It works, but 18px alone fixes the
  problem without changing a single coordinate, and the owner preferred the unchanged geometry.

#### The external-link mark, settled in the design session of 2026-09-23

This ticket was blocked again on 2026-09-23: the settled copy ends "**Create a token ↗**", Decision 6
forbids a typed glyph for a mark, and no drawn external-link mark existed. The owner ruled that an
external link needs a mark, and settled it on the browser companion.

**The mark is a box and arrow, named `external`, rendered at 14px inline with the link text:**

```
<path d="M14 5h5v5M19 5l-8 8M18 14v4.5A1.5 1.5 0 0 1 16.5 20h-11A1.5 1.5 0 0 1 4 18.5v-11A1.5 1.5 0 0 1 5.5 6H10"/>
```

- The geometry is the 2026-09-18 mockup's `#p-ext`, now at the set's **1.9 stroke**, round caps and
  joins, `currentColor`, on the 24px grid — no weight exception. The mockup's 2 stroke is dropped.
- **14px is a new context**, "inline with text", beside the rail's 16px and a row control's 18px. At
  16px it stands taller than the link's 13px text.
- It sits after the link text, takes the link's primary colour, and is `aria-hidden` like every
  mark; the link's accessible name stays "Create a token".
- Chosen over a bare up-right arrow and an arrow out of an open corner, because it says "external"
  most clearly.

**The issue keys stay bare.** They are external links too, but their tooltip already says "Open KEY
in Jira", and the owner chose not to mark them.

#### Out of scope

A mark on the issue keys, which stay bare by the owner's choice. Changing how tokens are stored, encrypted or validated. A connection test that probes write
access. Reworking the error a failed push reports
([CB#79](79.md)) and how failures are classified (CB#19).

#### Standing constraints

Vanilla JS with TypeScript for typing, Tailwind v4, light-DOM `that-*` WebComponents, and the 14kB
initial-response budget. No test may contact a real Jira instance.

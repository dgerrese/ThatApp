# CB#89: Settings: take it out of the nav and redesign the page

Archived from Codeberg issue [#89](https://codeberg.org/DionGerrese/ThatApp/issues/89), closed. Opened by DionGerrese on 2026-09-02, closed on 2026-09-29.

Milestone: v1.

**Why it is kept:** Settings redesign reasoning: the align-items:center scroll trap and Preflight margin trap behind margin:auto, why a test verdict is not stored, and the open failed-verdict-without-time question; the trap reasoning is in no spec or code.

## Body

#### Context

Raised in passing while designing CB#11, 2026-09-02. Recorded so it is not lost; nothing has been
decided.

The rail carries three destinations: Today, Week and Settings. The first two are *periods* — they
show time, they have a total, and under CB#11's design the rail describes whichever one you are in.
Settings is not a period at all. It shows no time, has no total, and gives the rail nothing to
describe.

That asymmetry is what CB#11 ran into. Its rail rule is "the rail describes the view you are in", and
Settings is the one view where that sentence has no meaning, so it falls back to today. The fallback
is free, because it is what the rail already does — but it exists only to paper over a destination
that does not belong beside the other two.

The owner's own framing: Settings might move out of the main navigation entirely, and might become a
dialog rather than a view.

#### Not yet decided

Whether Settings becomes a dialog, moves somewhere else in the shell, or stays. If it becomes a
dialog over whatever view is beneath it, the rail keeps describing that view and CB#11's fallback
clause becomes dead code worth deleting.

#### Notes for whoever picks this up

- `web/src/views/settings.ts` is a lazily imported view and `/settings` is a route in
  `web/src/router.ts`. Both would change.
- The nav lives in `web/index.html` and is part of the 14kB initial-response budget.
- `docs/superpowers/specs/2026-08-20-visual-design-language.md` specifies three rail destinations
  directly under Push, so it would need amending rather than quietly contradicting.
- CB#11's spec marks its Settings fallback as deliberately not load-bearing, so this can change
  without reopening CB#11.

#### Widened into the Settings redesign, 2026-09-03

The owner asked for a complete redesign of Settings and expected a ticket for it. This is that
ticket: its original question — does Settings belong in the nav at all — is the first question any
redesign has to answer, so the two are one piece of work rather than two.

Two problems, in the owner's words: **it does not belong in the nav**, and **the page has no shape**.

##### Settled in the design session of 2026-09-03

1. **A cog beside the wordmark**, at the rail's top right, not a nav row and not pinned to the rail's
   foot. The nav below it becomes what it claims to be: the two periods. The cog is drawn from
   computed gear geometry at a **1.7 stroke** rather than the set's 1.9 — it carries far more outline
   in the same space and the teeth close up at 16px otherwise. That is the only icon in the set with
   its own stroke weight and should be recorded as an exception.
2. **It opens a modal dialog**, using the native `<dialog>` pattern this app already uses twice. The
   view underneath stays mounted, so the rail keeps describing a real period — which makes **CB#11's
   fallback clause dead code worth deleting**, exactly as this ticket predicted, and turns the
   language's "three rail destinations" into two and a control.
3. **The dialog scrolls as one piece.** The top-layer element fills the viewport and is the scroller;
   the panel is an ordinary child with `margin: auto`, natural height and no cap. It centres when it
   fits and slides when it does not, with no scrollbar inside it. **The trap:** `align-items: center`
   on a scroll container centres by overflowing both edges, and a scroller cannot reach content above
   its start edge — the top of a tall panel becomes unreachable, silently. `margin: auto` does not
   have that failure. Also, Preflight's `* { margin: 0 }` already beat the UA's `dialog { margin:
   auto }` once in this codebase, so the panel's auto margin must be set explicitly.
4. **The shape.** The instance list is the subject. The add form becomes an **action** rather than
   furniture sitting permanently open below the list, which is most of why the page reads as three
   equal slabs today. Appearance is a compact row, last, because it can safely fall below the fold.
5. **Each instance states its own health**, beside its name — **on demand, never on open**. An
   untested instance reads *Not tested* in muted ink with no icon, so it never wears a colour that
   could be read as a verdict. A result carries the time it was taken, because a verdict without a
   timestamp becomes a claim about now. The failing case reads *Token cannot write*, which is where
   **[CB#80](80.md)** lands naturally and is the failure that has blocked every real push.
6. **Row controls are icon buttons** — test, edit, remove — going **primary** on hover, except remove
   which goes to the failed tone.
7. **The instance form's inputs sit at the bottom of their grid row**, so they line up with each
   other and a longer helper pushes only its own label up. The token's helper is its own muted line
   under the label: *Stored encrypted. It is never shown again.* while adding, *Leave blank to keep
   the stored one* while editing.
8. **The theme control is a three-way segment** — Dark, Light, System.

##### Settled: unset follows the system

Answered by the owner on 2026-09-03. **System is the unset state and follows `prefers-color-scheme`**,
so a machine set to light opens the app light. That is correct behaviour, not a defect.

"Dark is the default" means two narrower things: the root declares `color-scheme: dark light`, whose
order only decides the case where the platform expresses no preference; and dark is the ground the
palette was authored and measured in. A stored preference beats both. The segment therefore reads
**Dark · Light · System**, and the boot script is unchanged — an absent `data-theme` is the System
state, so a failed storage read follows the platform rather than guessing.

##### Also found

`that-entry-dialog.ts` uses `×` for close and for stop-editing. Those are two of the eight typed
glyphs the language's icon rule now forbids; the full inventory is in the language spec.

The design source is the prototype committed under CB#95 at
`docs/superpowers/prototypes/2026-09-03-app-prototype.html` — the cog, the dialog and the instance
form are all live in it.


#### Handed over from [CB#117](117.md)'s prototype audit, 2026-09-08

The audit compared the shipped app to `docs/superpowers/prototypes/2026-09-03-app-prototype.html`
view by view. **All seven of its Settings findings are covered by this ticket's own body** and are
not built in [CB#117](117.md). Two sub-parts of them are not named anywhere above, and are added here so the
redesign does not lose them:

- **Each instance row carries its instance dot and a host line.** The drawing gives every row the
  8px hue dot the rest of the app keys off instance position, and `host · email` beneath the name
  with the host in the mono face. The shipped row has neither, showing `email · siteUrl` in one
  muted line. This ticket already replaces the row's controls; the row's identity goes with them.
- **Whether a connection-test result survives a reload is still open.** This body settles the
  at-rest states and says a verdict carries the time it was taken, because "a verdict without a
  timestamp becomes a claim about now" — but it never says where that timestamp lives. Showing
  `Not tested` after every reload of an instance tested five minutes ago is the honest reading of
  the current code and probably not what is wanted, so it needs a stored last-tested time and a
  decision on whether that is a column or a cache.


#### Refined, 2026-09-21

The last open question is answered and this ticket is ready. **No design session was needed** — the
2026-09-03 session settled the shape and the [CB#117](117.md) audit filled in the row; only the verdict's
storage was still open.

##### Settled: a test result is not stored

**A connection-test verdict lives in memory for the lifetime of the page, and nowhere else.** No
migration, no column, no cache table.

This overrules the guess recorded above that showing *Not tested* after a reload "is probably not
what is wanted". It is what is wanted: a stored verdict is a claim about credentials that can be
revoked outside this app, so it ages badly, and the cheapest honest answer is to say nothing until
asked. The at-rest states are unchanged — *Not tested* in muted ink with no icon, and a result
carrying the time it was taken.

**In memory means the page, not the dialog.** A module-level map keyed by instance id, so closing
Settings and reopening it keeps the verdict and only a reload clears it. Clearing on every dialog
close would make storing it pointless. (Decided at refinement rather than asked; overrule if wrong.)

**Consequence:** this ticket touches no schema, adds no `THAT_*` variable, and needs no migration.

### DionGerrese, 2026-09-04 13:56

**Three things from the 2026-09-04 light pass land on this ticket's design.**

- **The cog's hover box escaped the rail's gutter.** It carried a negative right margin that pulled
  the glyph out to the content edge and took its 34px wash eight pixels into a fourteen-pixel gutter.
  Fixed in the prototype. The rule is now in the visual language: a hover box stays inside the padding
  of the region that holds it, and a control at a region's edge is aligned by matching that padding.
  The card rule — a control's ink meets the card edge — is scoped separately and still holds inside a
  card.
- **Settings must name its own ink.** It is a scroller sibling of the viewport, so it was inheriting
  its text colour from outside the app. Dark hid it completely: light text on a dark sheet is what it
  should look like anyway. As a top-layer `<dialog>` the redesigned version has the same problem
  waiting, because the top layer does not inherit from the view that opened it.
- **Elevation is now a rule**, decision 11 of the language, and it is per theme. On light the dialog
  carries its edge border plus `0 12px 36px -12px rgba(0,0,0,.16)` rather than dark's shadow. The
  segmented control's selected pill is in that table too.

Not settled, and worth deciding as part of this ticket rather than inheriting: **the scrim behind the
open dialog is still half-opaque black in both themes.** Raised separately.

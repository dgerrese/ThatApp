# CB#322: The release script sets :stable on a stable release, and the README updates from it

Archived from Codeberg issue [#322](https://codeberg.org/DionGerrese/ThatApp/issues/322), closed. Opened by DionGerrese on 2026-10-26, closed on 2026-10-26.

Milestone: Releases.

**Why it is kept:** Owner decisions on the release channels (:latest every release, :stable default) plus the declined 'promote a pre-release to stable without rebuild' and why CI can publish only pre-releases; the channels are in README/spec/plan but the declined promotion is recorded nowhere else.

## Body

Refined with the owner on 2026-10-26. CB#173 is merged into this ticket.

#### Problem

The image has two update channels, set by the owner on 2026-10-26:

- `:latest` follows **every** release, pre-releases included. This is intended.
- `:stable` is the **default update channel**. It moves only on a stable release.

`scripts/release-image.sh` knows only the first one. It pushes `REPO:VERSION` and moves `REPO:latest`, and it has no way to say that a release is stable. v2026.44.1, the first stable release, got its `:stable` tag by hand with `docker buildx imagetools create`.

`README.md` tells a colleague to run and upgrade from `:latest` (its three `docker run` commands and the upgrade's `docker pull`). That channel now gets pre-releases, so a colleague who follows the README runs pre-releases without knowing it.

#### Approach

1. **A third argument says a release is stable.** `release-image.sh VERSION REPO stable` also moves `REPO:stable` to the new index. With no third argument the release is a pre-release: `:latest` moves and `:stable` does not. So `:stable` never moves by accident. Any third argument other than `stable` is a usage error (exit 2), checked before anything is built.
   ```
   release-image.sh 2026.45.1 codeberg.org/diongerrese/thatapp          # :2026.45.1 :latest
   release-image.sh 2026.45.1 codeberg.org/diongerrese/thatapp stable   # :2026.45.1 :latest :stable
   ```
2. **The script checks what it pushed**, the same way it already checks `:latest` for both architectures: on a stable release, `:stable` resolves to the same digest as `:VERSION`. Its last line names every tag it moved.
3. **The tag-push workflow passes no third argument.** A tag push cannot read the Codeberg release's pre-release checkbox, because the release object does not exist yet when the tag starts the run. So CI can publish pre-releases only, and a stable release runs on this machine. Actions are off for the repository now anyway ([CB#284](284.md)).
4. **The dry runs take the stable path**, so the full path runs before a real stable release: `make image` and the workflow's pull-request dry run pass `stable` to the throwaway registry.
5. **`README.md` uses `:stable`** in all three `docker run` commands and in the upgrade's `docker pull`. It says in one or two sentences what the two channels are, and that `:latest` also gets pre-releases. The sentence about pinning to one version stays.
6. **The design of record** (`docs/superpowers/specs/2026-08-04-thatapp-design.md`, *Container layout*) says that the index is pushed as `VERSION` and `latest`, and also as `stable` on a stable release.

#### Acceptance criteria

- [x] `release-image.sh VERSION REPO` pushes `VERSION`, moves `latest`, and leaves `stable` where it was.
- [x] `release-image.sh VERSION REPO stable` also moves `stable`, and `stable` resolves to the digest of `VERSION`.
- [x] A third argument other than `stable` fails with exit 2 and a usage message, before any build.
- [x] The script's last line names each tag it moved.
- [x] `make image` runs the stable path against the throwaway registry, and passes.
- [x] `.forgejo/workflows/release.yml`'s pull-request dry run passes `stable`. Its tag-push publish passes no third argument.
- [x] `README.md` runs and upgrades from `:stable`, and explains the two channels.
- [x] The design of record's *Container layout* paragraph names the `stable` tag.
- [x] `make verify` and `make test-e2e` pass.

#### Out of scope

- **Promoting a published pre-release to stable later, with no rebuild.** The owner declined it for now. Until a ticket asks for it, the manual `docker buildx imagetools create -t REPO:stable REPO:VERSION` still works.
- **The workflow reading the pre-release checkbox**, for example through a `release: published` trigger. Actions are off, so it cannot be tested now.
- **Upgrading the owner's own `thatapp` container** to `:stable`. That is the owner's machine, not the product.

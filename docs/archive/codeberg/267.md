# CB#267: A tooltip cannot be dismissed with Escape or hovered, as WCAG 1.4.13 asks

Archived from Codeberg issue [#267](https://codeberg.org/DionGerrese/ThatApp/issues/267), closed. Opened by DionGerrese on 2026-09-30, closed on 2026-10-07.

Milestone: v1.

**Why it is kept:** Owner decision: Escape-only for WCAG 1.4.13, with hoverability knowingly unmet to keep CB#107's pointer-events:none; the code comment records only the Escape half, not the recorded non-compliance.

## Body

#### Problem

Found on 2026-09-30 while checking CB#246's tooltip contrast for accessibility.

WCAG 2.2 success criterion 1.4.13 (Content on Hover or Focus, level AA) asks three things of content that appears on hover or focus:

- **Dismissible:** it can be closed without moving the pointer or focus, usually with Escape. `that-tooltip` has no key handling, so a shown tooltip stays until the pointer leaves or focus moves.
- **Hoverable:** the pointer can move onto the content without it disappearing. `that-tooltip` hides on the trigger's `pointerleave`, and CB#107 gave every tooltip `pointer-events: none` so a tooltip can never catch a click.
- **Persistent:** it stays until one of those happens. This one holds today.

Related: CB#107 (tooltip after the dialog closes, and `pointer-events: none`), [#10](https://github.com/dgerrese/ThatApp/issues/10) (a tooltip is never the accessible name).

#### Decision

Decided by the owner on 2026-10-06: **Escape only.** Escape closes a shown tooltip. Tooltips stay *not* hoverable: every tooltip keeps `pointer-events: none` and still closes when the pointer leaves its trigger, so CB#107's guarantee stands unchanged. The hoverable part of 1.4.13 stays knowingly unmet; this is a recorded choice, not an oversight.

#### Approach

In `that-tooltip`, while the popover is open, an Escape keydown hides it. The tooltip stays closed until the next pointer enter or keyboard focus on its trigger re-reveals it.

Escape must not do two jobs at once. Where Escape already means something to the control under it — closing a `<dialog>` opened with `showModal()`, closing the issue search field — the first Escape with a tooltip open closes **only the tooltip**, and the next Escape does what it did before. Confirmed by the owner on 2026-10-06. It is the usual pattern for 1.4.13 and keeps a keyboard user from closing a dialog while dismissing its tooltip.

#### Acceptance criteria

- [x] With a tooltip open from hover, pressing Escape closes it while the pointer stays on the trigger.
- [x] With a tooltip open from keyboard focus, pressing Escape closes it while focus stays on the trigger.
- [x] After Escape, the same tooltip opens again on the next pointer enter or keyboard focus of its trigger.
- [x] Inside the entry dialog, Escape with a tooltip open closes the tooltip and leaves the dialog open; a second Escape closes the dialog.
- [x] In the issue search field, Escape with a tooltip open closes the tooltip and leaves the field open; a second Escape closes the field.
- [x] Escape with no tooltip open behaves exactly as on `main` everywhere.
- [x] Every tooltip keeps `pointer-events: none`; CB#107's tests still pass unchanged.
- [x] Each new or changed assertion is proven by mutation.
- [x] `make verify` and `make test-e2e` are green.

#### Out of scope

- Making tooltips hoverable — declined on 2026-10-06, see *Decision*.
- Any change to what a tooltip says or where it opens.

# CB#183: A running timer's figure and the Today sort disagree

Archived from Codeberg issue [#183](https://codeberg.org/DionGerrese/ThatApp/issues/183), closed. Opened by DionGerrese on 2026-09-22, closed on 2026-09-23.

Labels: `priority/high`.

Milestone: v1.

**Why it is kept:** Owner chose direction 2 (sort on displayed figure, re-sort only on start/stop/switch, never on tick); rejected re-sort-per-tick and excluding the running row; accepted drift ceiling is not recorded outside a one-line code comment.

## Body

#### The problem

Today's tables sort the **Today** column on a row's `seconds` attribute, which holds the seconds
**already logged**. The figure the row shows is `seconds + elapsed`, computed when the cell paints.

While a timer runs, those two drift apart, so the visible order can disagree with the visible
figures. Sorted by Today descending, a running row reading `3:05` can sit below a row reading
`3:00`.

- The comparator: `case "today": return a.seconds - b.seconds;` in `web/src/table-sort.ts`.
- The observed attributes: `["key", "summary", "status", "seconds"]` in
  `web/src/components/that-table.ts`. A tick changes the rendered text inside a cell, and
  `isOwnRowChange` deliberately ignores anything that is not a direct child of `tbody`.
- The figure: `durationSeconds()` in `web/src/components/that-ticket-row.ts` adds `elapsedSeconds()`
  when the running timer is this row's.

#### Why neither ticket is wrong on its own

[CB#83](83.md) (sorting) and CB#8 (the timer) were developed on separate branches and only met when CB#8 was
rebased onto current `main` on 2026-09-22. Each behaves correctly alone.

#### What refinement has to settle

**The obvious fix is worse than the problem.** Re-sorting on every tick would make a table sorted by
Today reorder itself once a second while the user reads it. That is why the observer ignores
in-cell changes, and that decision should not be undone without a reason.

Candidate directions, none chosen:

1. **Leave the order alone and say so** — accept that a running row keeps its place until something
   else re-sorts, and decide whether anything on screen has to signal it.
2. **Sort on the displayed total, but only re-sort on events that already re-sort** — a start, a
   stop, a switch, a refresh — not on ticks.
3. **Exclude a running row from the sort** and give it a fixed position, top or bottom.

Whether this needs a design session is itself an open question: option 3 puts something on screen
the design does not draw, options 1 and 2 do not.

#### Out of scope

The Week grid. It has no per-row sort and no live figure.

---

#### Refined, 2026-09-23

**Settled with the owner: direction 2.** The Today sort compares the figure a row *shows* — logged
seconds plus the running timer's elapsed time when the timer is that row's — but the table re-sorts
only on events that already re-sort it, plus a timer start, stop or switch. **A tick never re-sorts.**

So the order is right every time the table sorts, and it can drift only while a single run is under
way. A stop re-sorts with the final figure, so the drift ends with the run.

**No design session.** Nothing new goes on screen; the table's existing sort mark and behaviour are
unchanged.

**The known ceiling, accepted:** during a long run the running row can overtake a neighbour and stay
below it until the next event. Only the running row can drift, and its figure only goes up.

#### Acceptance criteria

- [x] Sorting by Today compares each row's displayed figure: `seconds`, plus `elapsedSeconds()` when
      `isRunningTicket(instance-id, key)` is true for that row. One definition of that figure serves
      both the cell and the sort, so the two cannot drift apart again.
- [x] The table re-sorts when the timer starts, stops or switches ticket (`onTimerChanged`), in
      addition to what re-sorts it today.
- [x] A timer tick does not re-sort. The observer's rule of ignoring in-cell changes stays as it is.
- [x] A node test on the comparator: a running row with fewer logged seconds but a larger displayed
      figure sorts above a stopped row, in descending order — and fails if elapsed time is ignored.
- [x] A Playwright spec on Firefox and Chromium: sort Today descending, start a timer on a row whose
      logged time is just below its neighbour's, let the run carry it past, trigger a start/stop, and
      assert the row order matches the displayed figures. It must also assert that the order does
      **not** change on ticks alone.
- [x] `make verify` and `make test-e2e` are green.

#### Out of scope

- The Week grid, which has no per-row sort and no live figure.
- Re-sorting at the moment the running row overtakes a neighbour. Rejected as a table that moves
  while it is read; reopen as its own ticket if the drift turns out to matter in use.
